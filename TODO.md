# Known problems

- `yo cp` drops build output in the staging directory after scp has already transferred it, so pulling a tree with a large `node_modules` still moves those bytes (`drop_from_staging` in `yo`, `yo.md#downloads-never-land-build-output`). The fix is a transport that excludes on the guest side: tar with `--exclude` over ssh, or a guest-side listing that feeds scp the paths to fetch. scp has no exclude option. Such a change must keep the CONSTITUTION rules for `yo cp`: glob-escape every guest source and never a destination, stage beside the destination and plan the merge before anything moves, and keep the control-path skip. It must also keep `-p` (see `yo.md#yo-cp`), because `unlock_tree` and the landed directory modes depend on how scp -p shapes them; a tar transport would need `--same-permissions` semantics and the same unlock step.
- pi's LSP (pi-lens) finds basedpyright on PATH only. direnv is gone, so a project's devbox is on pi's PATH only when pi runs inside `devbox shell`; pi started from a plain shell has no basedpyright. Check whether pi-lens can be given a launch command (then point it at `lspWrapper` in `nix/lsp.nix`), or whether herdr should start pi panes through `devbox run`.
- The throwaway-instance rescue for a box stuck in its initrd (a second lima instance with this instance's `disk` file attached) is untested. See `docs/disk-encryption.md#recognising-failures`.
- Verify on a live box that `yo ssh` drops when an exit node is selected without `--exit-node-allow-lan-access`. The flag itself is verified (see `nix/tailscale.md#exit-nodes`); the no-flag half is still only an expectation. Check on a box built without the flag: `yo ssh sudo tailscale set --exit-node=<node>`, then see whether `yo ssh` survives.
- `limactl stop yolobox` hangs on the vz driver (lima 2.2.0 and 2.2.1); see the lima entry under Upstream.
- The swapfile size is unconditional (`swapDevices` in `nix/base.nix` is 16 GiB on every disk), and a full root disk shows up as a DNS failure instead of a disk error: `dhcpcd` gets ENOSPC, `/etc/resolv.conf` is left at 0 bytes, and `tailscale up` loops on "failed to resolve". Seen on the 30 GiB `e2e-test` instance (16 GiB swapfile plus 13 GiB nix store). `yo.md#several-instances` now states a 40 GiB floor, but nothing enforces it. Candidate fixes: a free-space check in `net-check` and `yo status` that names the full disk, and a swap size that a box's `/etc/yolobox/local.nix` can set (or that scales with the disk) without `lib.mkForce`.
- The Python 3.9 unit leg in `.github/workflows/verify.yml` is pinned to `ubuntu-24.04`, because setup-python has no 3.9 build for ubuntu-latest's 26.04 image. The pin will age out when GitHub retires the 24.04 image. Then run the leg in a `python:3.9` container as a non-root user with `jq` and `gawk` installed (as root with those missing, 26 tests fail and 2 skip), or drop the floor along with the Mac's Xcode Python 3.9.
- conmon 2.2.1 (podman 5.8.8) writes `Failed to open cgroups file: /sys/fs/cgroup/memory.events` once per healthcheck run, and the cause is unexplained (22 percent of the 2.5 million journal lines in the incident in `nix/podman.md`). `nix/podman.nix` does not remove it: conmon's own stderr goes to the journal whatever the log driver and events logger are, so only `SystemMaxUse` bounds it. Evidence so far:
  - The text comes from `check_cgroup2_oom()` in conmon's `src/cgroup.c`. It opens `<cgroup2_path>/memory.events`, and the path in the message means `cgroup2_path` was `/sys/fs/cgroup` plus `/`: the cgroup path of the exec'd healthcheck process read as `/`.
  - `process_cgroup_subsystem_path()` in v2.2.1 takes the path from the first line of `/proc/<pid>/cgroup` whatever it is. conmon's `main` now skips every line that is not `0::` and says so in a comment. That is the best lead, but a cgroup v1 line has not been seen on this box: `/proc/mounts` shows only the unified hierarchy and the container processes show a single `0::` line.
  - Not reproduced with throwaway containers on the box: a `true` healthcheck, a `sleep 1` one, a `wget | grep` one on the same image as an affected container, each started by the CLI and by compose through the docker API socket. Every affected container belonged to one compose stack whose 14 healthchecks fire in the same second, and one container of that stack never warned. A single container never showed it.
  - Next step: when it shows again, capture `/proc/<exec pid>/cgroup` from a transient `podman healthcheck run` unit while it runs, and try a conmon built from `main`.
- AF_VSOCK from the guest to the host (CID 2) is not seen by the egress table. A live probe found no listener: every port tried on CID 2 answers with a connection reset, because Lima runs with `overVsock:false` and nothing listens host-side. So nothing is reachable today. This is an accepted residual (see `nix/egress.md#residuals`). A future host-side vsock listener would be entirely outside the table's reach.
- Proton provider for the private `yolobox-egress` module (the tunnel that owns egress): dropped from v1, because Proton has no supported config API. Importing a downloaded WireGuard `.conf` is the likely route.
- IPv6 under Tor in `yolobox-egress`: needs a `[::1]` TransPort and a v6 route into `lo`. Until then v6 is not carried through Tor.
- The box has no global IPv6. `enp0s1` has only an fe80 link-local address, there is no IPv6 default route, and only `tailscale0` carries a v6 address (a ULA). So Lima's NAT gives the box no global IPv6. The IPv6 form of the host-address hairpin is unreachable unless the host gains global v6 and Lima assigns the guest a global v6 default. See `nix/egress.md#residuals`.
- GitHub `environment: release` protection for HOMEBREW_TAP_TOKEN not configured.
- Tailnet ACLs for the yolobox node not reviewed. `tailscale0` is trusted, so the ACL is the only access control: every node it admits reaches every port of the box (see `nix/tailscale.md#firewall`).
- tailscaled on the box logs `new contact: peer=[...] via=derp` about every 6 s for one peer. The cause has not been investigated; possibly a peer that never gets a direct path.
- Immutable releases must stay off: release.yml force-moves the tag and re-uploads with --clobber.
- Secrets that still live on disk despite the constitution's rule: lima's instance ssh key (`~/.lima/_config/user`, lima owns it), the agent's vendor credentials (`~/.claude`, `~/.config/gh`, `fj auth`), and the stage-2 sshd host keys. Each is a vendor's own storage; the rule forbids this repo from adding to the list, and the LUKS root now covers the guest-side ones at rest.
- Several instances (`YOLOBOX_INSTANCE`, see `yo.md#several-instances`) share some host-global state. Each item below breaks, or is weaker, once two or more boxes run at once; nothing was changed for them:
  - The LUKS key is one 1Password item (`yolobox-disk`) and the passphrase derives from it alone, so every instance's disk opens with the same passphrase. Whoever holds it for one box holds it for all, and rotating it needs every disk re-keyed.
  - The AWS broker has one socket (`~/.local/state/yolobox/aws-broker.sock`) and one watched hostagent pid (`ensure_aws_broker`, `broker_needs_restart`). When two boxes are up, each `yo` run restarts the broker to watch its own box's hostagent, and stopping the watched box ends the broker, so the other box loses its AWS credentials until its next `yo` run. Only matters where `aws` is installed and has SSO profiles.
  - `yo link` always names the git remote `yolobox`. `yo link` for a second instance in a repo already linked to the first fails with "remote 'yolobox' points at ... which is not this VM" until the first remote is removed, so a repo can be linked to one box at a time.
  - `lima/yolobox.yaml` mirrors guest TCP ports 1024-49151 onto the host's 127.0.0.1, same number on both sides. Two running boxes that listen on the same port collide: the second hostagent cannot bind it and lima logs the failure while the first box keeps the port.
  - `nix/luks/yolobox-luks-migrate.sh` prints `ssh in as root on port 60022` (the constant from `nix/luks/facts.nix`) when it refuses an encryption for lack of space. On a non-default instance the real port is the one in its `ssh.localPort`. The yo-side messages already print the right one.

## Security hunt (2026-10-31)

Confirmed findings that this pass did not fix. Each one names its evidence and a candidate fix.

- **F2 port-mirror squat (MEDIUM).** Lima mirrors guest TCP ports 1024-49151 onto the host's `127.0.0.1`, minus the small deny-list in `lima/yolobox.yaml`. An agent can bind an in-range port before a host tool does. A host connection to that `127.0.0.1` port then reaches the guest listener, so real bytes cross. This was proven with an unused port: a host `nc` to `127.0.0.1:PORT` received the guest's payload. Usually the squat only denies the port, because the host tool then fails to bind. But a browser that navigates to `localhost:PORT` for a dev or OAuth flow, whose real server never bound, would reach the guest. Candidate fixes: shrink the mirror range, extend the deny-list with known callback ports, or make the mirror opt-in per port. Reproduction: as the agent, bind `0.0.0.0:34567` in the guest, then on the host run `nc -z 127.0.0.1 34567`.
- **F5 AWS broker slot exhaustion (LOW-MED).** `aws-broker` caps concurrency at 32 slots with a `BoundedSemaphore`. Its per-connection timeout is a per-recv socket timeout, which resets on every byte, so it is not a wall-clock deadline. A client that trickles bytes holds a slot indefinitely, and 32 such clients deny the broker. One broker serves every running box, so in a multi-box setup one box can starve another box's AWS credentials. The damage is bounded, because any `yo` run restarts the broker and clears the slots. No secret leaks on the error paths, since the broker requires a SessionToken. Fix: a total wall-clock deadline per request.
- **F1 residual, the `yo cp` overwrite.** The control-path overwrite is closed: `yo cp` never lands in `.git`, `.hg`, `.svn`, `.envrc`, `.vscode` or `.idea`. The broader residual remains. `yo cp` still overwrites ordinary existing files during a merge, which is the documented "pull my work back" behavior. An operator who pulls a guest tree onto an existing tree should still review it, because the pull is already the sandbox trust boundary (see `CONSTITUTION.md`).
- **D1 1Password forward exposes every vault key (HIGH blast radius, as designed).** The forwarded agent serves every key in the Private and "Iurii Technologies" vaults, because `agent.toml` filters by vault only. That includes `yolobox-disk` and the GitHub and Scaleway keys. `LUKS_SIGN_DATA` is public and the derivation is deterministic, so one approved `yolobox-disk` signature yields the disk passphrase. The per-sign 1Password prompt is the only gate. Candidate fix: a per-key or per-item filter, or a dedicated forwarded socket that exposes only what the box needs.
- **D2 supply chain: the flake ref is a movable tag with no rev pin (HIGH, as designed).** `yo` builds from `github:aka-rider/yolobox/v<version>`. The release workflow force-moves that tag. `nixos-rebuild` runs as root in the guest and fetches the mutable tag, which also builds the initrd and the LUKS unlock. So an owner, token or tag compromise gives root in the guest and in the initrd on the next operator-initiated rebuild. The agent cannot trigger this, so it is trust-on-first-use. The harness installers are also unpinned `curl | bash`, which stays contained to the agent. Candidate fix: have the Mac pass a rev and narHash that the guest verifies, and checksum the installers.
