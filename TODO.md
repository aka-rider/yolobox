- lima issue, not yet written up: `limactl stop yolobox` (and the stop half of `limactl restart`) hangs on the `vz` driver, lima 2.2.0 and 2.2.1. Five sightings, none isolated to a trigger:
  - 2026-09-05, a throwaway instance whose forwards were dead: three minutes, then `did not receive an event with the "exiting" status`; the host agent never exited and `limactl delete -f` was the only way out.
  - 2026-09-28, during the AWS broker transport spike, with no dead-forward state involved: the same message, the guest-agent grpc stream reset partway through, and a child `limactl hostagent` (parent: the real hostagent) spinning at ~98% CPU that outlived `limactl stop -f` of its parent and had to be `kill -9`'d.
  - 2026-10-01: the same again, the child spinning at ~99% and still alive after the guest rebooted from inside.
  - 2026-10-17, lima 2.2.1, `yo bootstrap`'s `limactl restart` after five days of uptime: the same message after three minutes. The hostagent took SIGINT, stopped the 1Password reverse forward, kept logging time-sync lines, and never exited. A second `limactl hostagent` spun at ~86% CPU. A later plain `limactl stop` worked.
  - 2026-10-24, lima 2.2.1, the first `yo down` before the LUKS migration: three minutes, then `did not receive an event with the exiting status`; `lima_stop()` printed its recovery text. Recovered by `kill -9` of the hostagent while the box waited in its initrd (under vz that also ends the VM). The second stop, done by `vm_up` after the migration, worked.

  The gentler recovery when `limactl stop` hangs is `sudo systemctl reboot` inside the guest (`yo ssh sudo systemctl reboot`); the child still needs `kill -9`. Not written up until a narrower repro exists.

# Known problems

- The throwaway-instance rescue for a box stuck in its initrd (a second lima instance with this instance's `disk` file attached) is untested. See `docs/disk-encryption.md#recognising-failures`.
- Verify on a live box that `yo ssh` drops when an exit node is selected without `--exit-node-allow-lan-access`, and stays up with it: `yo ssh sudo tailscale set --exit-node=<node>`, then check `yo ssh` survives. The flag's expected effect is in `nix/tailscale.md#exit-nodes`. Once checked, remove the "not yet verified" notes in `nix/tailscale.nix` and `nix/tailscale.md`.
- `limactl stop yolobox` hangs on the vz driver (lima 2.2.0 and 2.2.1); see the lima entry under Upstream.
- The Python 3.9 unit leg in `.github/workflows/verify.yml` is pinned to `ubuntu-24.04`, because setup-python has no 3.9 build for ubuntu-latest's 26.04 image. The pin will age out when GitHub retires the 24.04 image. Then run the leg in a `python:3.9` container as a non-root user with `jq` and `gawk` installed (as root with those missing, 26 tests fail and 2 skip), or drop the floor along with the Mac's Xcode Python 3.9.
- conmon 2.2.1 (podman 5.8.8) writes `Failed to open cgroups file: /sys/fs/cgroup/memory.events` once per healthcheck run, and the cause is unexplained (22 percent of the 2.5 million journal lines in the incident in `nix/podman.md`). `nix/podman.nix` does not remove it: conmon's own stderr goes to the journal whatever the log driver and events logger are, so only `SystemMaxUse` bounds it. Evidence so far:
  - The text comes from `check_cgroup2_oom()` in conmon's `src/cgroup.c`. It opens `<cgroup2_path>/memory.events`, and the path in the message means `cgroup2_path` was `/sys/fs/cgroup` plus `/`: the cgroup path of the exec'd healthcheck process read as `/`.
  - `process_cgroup_subsystem_path()` in v2.2.1 takes the path from the first line of `/proc/<pid>/cgroup` whatever it is. conmon's `main` now skips every line that is not `0::` and says so in a comment. That is the best lead, but a cgroup v1 line has not been seen on this box: `/proc/mounts` shows only the unified hierarchy and the container processes show a single `0::` line.
  - Not reproduced with throwaway containers on the box: a `true` healthcheck, a `sleep 1` one, a `wget | grep` one on the same image as an affected container, each started by the CLI and by compose through the docker API socket. Every affected container belonged to one compose stack whose 14 healthchecks fire in the same second, and one container of that stack never warned. A single container never showed it.
  - Next step: when it shows again, capture `/proc/<exec pid>/cgroup` from a transient `podman healthcheck run` unit while it runs, and try a conmon built from `main`.
- AF_VSOCK from the guest to the host (CID 2) is not seen by the egress table. Check whether Lima's vz driver registers any host-side vsock listener a guest could dial (a guest `socat - VSOCK-CONNECT:2:<port>` against the ports the hostagent holds). If one exists, close it or document it in `nix/egress.md#residuals`.
- Proton provider for the private `yolobox-egress` module (the tunnel that owns egress): dropped from v1, because Proton has no supported config API. Importing a downloaded WireGuard `.conf` is the likely route.
- IPv6 under Tor in `yolobox-egress`: needs a `[::1]` TransPort and a v6 route into `lo`. Until then v6 is not carried through Tor.
- Check on a live box whether Lima's NAT gives the vanilla box IPv6 at all (`ip -6 addr`, `ip -6 route`, `curl -6 https://ifconfig.co`). The answer decides whether the IPv6 entry above matters.
- GitHub `environment: release` protection for HOMEBREW_TAP_TOKEN not configured.
- Tailnet ACLs for the yolobox node not reviewed. `tailscale0` is trusted, so the ACL is the only access control: every node it admits reaches every port of the box (see `nix/tailscale.md#firewall`).
- tailscaled on the box logs `new contact: peer=[...] via=derp` about every 6 s for one peer. The cause has not been investigated; possibly a peer that never gets a direct path.
- Immutable releases must stay off: release.yml force-moves the tag and re-uploads with --clobber.
- Secrets that still live on disk despite the constitution's rule: lima's instance ssh key (`~/.lima/_config/user`, lima owns it), the agent's vendor credentials (`~/.claude`, `~/.config/gh`, `fj auth`), and the stage-2 sshd host keys. Each is a vendor's own storage; the rule forbids this repo from adding to the list, and the LUKS root now covers the guest-side ones at rest.
