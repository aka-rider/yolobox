# Upstream

The reasoning is in lima/yolobox.md#an-empty-page-means-limas-forwarder-died. The lima side is done: lima-vm/lima#5557 was closed, PR #5558 merged, and the fix shipped in lima v2.2.1. What remains is the nixos-lima change below.

- nixos-lima PR [nixos-lima/nixos-lima#125](https://github.com/nixos-lima/nixos-lima/pull/125): `restartIfChanged = false` on `lima-init` and `lima-guestagent`, because a nixpkgs bump alone restarts them and, on lima v2.1.2 through v2.2.0, that triggers the dead-forward bug. Still open and unmerged.
  - Once it is merged and this flake's `nixos-lima` input is bumped, this repo's own pin (`systemd.services.lima-guestagent.restartIfChanged` and `lima-init.restartIfChanged` in `nix/base.nix:118-119`) becomes redundant: remove it.
- lima: `limactl stop` (and the stop half of `limactl restart`) can hang on the `vz` driver, seen on lima 2.2.0 and 2.2.1, with no isolated trigger. Symptom: after about three minutes `did not receive an event with the "exiting" status`; the hostagent took SIGINT, stopped some forwards, and never exited, and a child `limactl hostagent` may spin at high CPU and outlive `limactl stop -f` of its parent. `LimaDriver.stop` prints its recovery text. Recovery: `kill -9` the hostagent (and the spinning child); under vz that also ends the VM. A gentler route is `sudo systemctl reboot` inside the guest (`yo ssh sudo systemctl reboot`), though the child still needs `kill -9`.

# Known problems

## Not yet run on a live box

- The Lima path has not been run live since `yo` was split into a Lima and a libvirt driver and then into the `yolobox_cli/` package. The whole unit suite is green on a Linux CI host, but `limactl`, vz, the port mirror and the reverse forwards were last exercised on a Mac before the split, and the brew formula's directory install (`libexec.install "yo", "aws-broker"`, the `yolobox_cli` tree minus `libvirt.py` and `libvirt_host.py`, and the `inreplace` of `YO_VERSION` in `yolobox_cli/config.py`) has never been built. Before the next release, on a Mac: `brew install --build-from-source` the formula and `brew test yolobox` (an `inreplace` that matches nothing ships a `yo` that reports `dev`, see `yo.md#yo_version`), then run `yo up`, `yo status`, `yo bootstrap` and `tests/box-hardening-e2e.sh` against a throwaway instance.
- The throwaway-instance rescue for a box stuck in its initrd (a second lima instance with this instance's `disk` file attached) is untested. See `docs/disk-encryption.md#recognising-failures`.
- Verify on a live box that `yo ssh` drops when an exit node is selected without `--exit-node-allow-lan-access`. The flag itself is verified (see `nix/tailscale.md#exit-nodes`); the no-flag half is still only an expectation. Check on a box built without the flag: `yo ssh sudo tailscale set --exit-node=<node>`, then see whether `yo ssh` survives.
- `yo bootstrap`'s reboot on a libvirt host once reported the `virsh shutdown` as failed after the 300 s `virsh event` window, yet the domain was already `shut off` when checked; `yo up` then booted the built generation. The event race behind that is fixed (`LibvirtDriver.stop` arms one `virsh event --loop --timeout` before the shutdown and re-reads `domstate` after every line, see `yo.md#the-libvirt-driver`). The other explanation, a guest that really took about 300 s to power off, was not reproduced: on a throwaway libvirt box (2026-11-03) `yo down` took 1.2 s and the guest journal showed power-off 0.6 s after the shutdown request, with no unit timing out. Kept only until a bootstrap reboot has been seen to complete without the 300 s wait on a real box; delete it then.
- `yo down` on a box parked in its initrd (locked, waiting for the passphrase) may hang for the full stop timeout (300 s) on both drivers: the initrd has no ACPI handler, so the shutdown request is never acted on. Unconfirmed. Check: leave a rebooted box at the passphrase prompt (do not run `yo up`), then time `yo down`. Candidate fix: if `boot_stage()` says the box is in the initrd, skip the polite shutdown and go straight to the driver's forced stop (`virsh destroy`, `limactl stop -f`), since nothing there needs a clean exit.

## Several machines

`yo -m NAME` (see `yo.md#several-machines`) shares some host-global state. Each item below breaks, or is weaker, once two or more boxes run at once; nothing was changed for them:

- The LUKS key is one 1Password item (`yolobox-disk`) and the passphrase derives from it alone, so every instance's disk opens with the same passphrase. Whoever holds it for one box holds it for all, and rotating it needs every disk re-keyed.
- The AWS broker has one socket (`~/.local/state/yolobox/aws-broker.sock`) and one watched pid (`ensure_aws_broker`, `broker_needs_restart` in `yolobox_cli/aws.py`). When two boxes are up, each `yo` run restarts the broker to watch its own box's keepalive pid, and stopping the watched box ends the broker, so the other box loses its AWS credentials until its next `yo` run. Only matters where `aws` is installed and has SSO profiles. The broker's own start-up races are under [aws-broker](#aws-broker) below.
- `yo link` always names the git remote `yolobox`. `yo link` for a second instance in a repo already linked to the first fails with "remote 'yolobox' points at ... which is not this VM" until the first remote is removed, so a repo can be linked to one box at a time.
- `lima/yolobox.yaml` mirrors guest TCP ports 1024-49151 onto the host's 127.0.0.1, same number on both sides. Two running boxes that listen on the same port collide: the second hostagent cannot bind it and lima logs the failure while the first box keeps the port. The same mirror is the port-mirror squat in the [Security backlog](#security-backlog).
- `nix/luks/yolobox-luks-migrate.sh` prints `ssh in as root on port ${YOLOBOX_SSH_LOCAL_PORT}` when it refuses an encryption for lack of space, and that value is baked in at build time from `sshLocalPort` in `nix/luks/facts.nix` (60022, the default instance's). On a non-default instance the real port is the one in its `ssh.localPort`. The yo-side messages already print the right one.

## Linux host

- `yo disk-grow` is not implemented for libvirt boxes (`LibvirtDriver.disk_ceiling_gib` and `grow_disk` raise). It needs `virsh vol-resize` while the domain is stopped, then the same `cryptsetup resize` and `resize2fs` steps `cmd_disk_grow` already runs.
- The ACL that lets `yolobox-vm` bind in `/run/libvirt/qemu/passt` is not durable. `host-setup.sh` step (j) installs a tmpfiles rule that applies `u:yolobox-vm:rwx` (with `m::rwx`) at boot, but when libvirt later starts another passt domain or changes the directory's mode, the ACL mask is recomputed to `r-x`, and the entry's effective permission drops with it: `getfacl /run/libvirt/qemu/passt` then shows `user:yolobox-vm:rwx #effective:r-x` and `mask::r-x`, and a yolobox `virsh start` fails with `Failed to bind UNIX domain socket: Permission denied`. Observed on a host that also ran a non-yolobox passt domain. `yo up` and `yo status` check the effective ACL and print the remedy (`docs/linux-host.md#recognising-failures`), but nothing keeps it fixed. Candidate durable fixes: a systemd path unit (or a `PathChanged=` on the directory) that re-applies the ACL with its mask (`setfacl -m u:yolobox-vm:rwx,m::rwx`), or an upstream libvirt change so the directory is not reset.
- An unprivileged `yo` cannot verify that the egress table is loaded: `nft list table` needs root, so `check_libvirt_host` sees only `systemctl is-active yolobox-host.service`. An operator who deleted the table without stopping the unit (see `linux/host-setup.md#the-host-table`) leaves a unit that reads `active` and a host with no table. Candidate fix: a root-owned oneshot that writes the table's presence to a world-readable file, or a handle `yo` can read without privilege.
- The owner check before each passphrase send (`LibvirtDriver.verify_initrd_listener`) is not atomic with the ssh connect, and a port with no listener passes it. A local process that binds the box's loopback port in that gap would receive the answer to the initrd's ssh handshake. The port sits above the kernel's ephemeral range, so only a deliberate squat can do it. Candidate fix: have ssh connect through a descriptor `yo` verified with `SO_PEERCRED`-style checks, or pin the initrd's host key through the domain.
- `yo` has no command to delete an instance. A libvirt box is removed by hand: `virsh -c qemu:///system destroy yolobox-NAME`, `undefine yolobox-NAME --nvram`, `vol-delete yolobox-NAME.qcow2 default` and `vol-delete yolobox-NAME-cidata.iso default`, then `rm -r ~/.local/state/yolobox/instances/NAME`. A Lima box is removed with `limactl delete`. A `yo delete` would need to refuse a running box and print what it removes.
- A box on a Linux host with global IPv6 has a global address, where a Mac box has none (`docs/linux-host.md#ipv6`). Both egress tables reject the same v6 ranges, but a LAN machine with a global address cannot be told from the internet. Candidate fix: give the domain no IPv6 (passt `--ipv4-only`, if libvirt exposes it) and say so in the story.

## Guest

- The swapfile size is unconditional (`swapDevices` in `nix/base.nix` is 16 GiB on every disk), and a full root disk shows up as a DNS failure instead of a disk error: `dhcpcd` gets ENOSPC, `/etc/resolv.conf` is left at 0 bytes, and `tailscale up` loops on "failed to resolve". `yo.md#several-machines` states a 40 GiB floor, but nothing enforces it. Candidate fixes: a free-space check in `net-check` and `yo status` that names the full disk, and a swap size that a box's `/etc/yolobox/local.nix` can set (or that scales with the disk) without `lib.mkForce`.
- Kernel bugs behind unprivileged user namespaces. The agent can `unshare -Urn`, become root of its own namespace and make the kernel autoload `nf_tables` and the net/sched modules, whose bugs have given root before (CVE-2024-1086, CVE-2023-32233, CVE-2022-2588). The box keeps user namespaces because the chromium sandbox, rootless podman and the nix build sandbox need them, and it keeps `nf_tables` because the firewall and podman's bridge networks sit on it. So today the only mitigation is a current kernel (`linuxPackages_latest` in `nix/base.nix`). Next step: the net/sched modules are idle unless a box configures traffic control, so try blocking `cls_*`, `act_*` and the other `sch_*` names, then run `tests/box-hardening-check.sh` and check tailscale and podman networking. The `nf_tables` half has no fix at the box level. See `nix/hardening.md#known-residual-the-surface-behind-user-namespaces`.

## `yo` and the repo

- `yo cp` drops build output in the staging directory after scp has already transferred it, so pulling a tree with a large `node_modules` still moves those bytes (`drop_from_staging` in `yolobox_cli/cp.py`, `yo.md#downloads-never-land-build-output`). The fix is a transport that excludes on the guest side: tar with `--exclude` over ssh, or a guest-side listing that feeds scp the paths to fetch. scp has no exclude option. Such a change must keep the CONSTITUTION rules for `yo cp`: glob-escape every guest source and never a destination, stage beside the destination and plan the merge before anything moves, and keep the control-path skip. It must also keep `-p` (see `yo.md#yo-cp`), because `unlock_tree` and the landed directory modes depend on how scp -p shapes them; a tar transport would need `--same-permissions` semantics and the same unlock step.
- `cmd_bootstrap` writes `~/.local/state/yolobox/<name>.flake-ref` with a plain `open(..., "w")` (`yolobox_cli/vm.py`). A crash or Ctrl-C between the truncate and the write leaves an empty file, which `remembered_flake_ref` reads as no ref, so the next printed rebuild remedy silently names this `yo`'s release instead of the fork the box was built from. Candidate fix: `proc.atomic_write(release.flake_ref_file(), ref + "\n", 0o644)`.
- `cmd_enter` passes `-t` to ssh unconditionally (`yolobox_cli/session.py`), while `cmd_ssh` passes it only when stdin and stdout are both terminals. With stdin redirected, `yo enter` makes ssh print "Pseudo-terminal will not be allocated because stdin is not a terminal" and run the login shell without a pty. Candidate fix: refuse with a clear error when stdin or stdout is not a terminal, since `enter` exists to give an interactive shell (and then `-t` is right as it stands), or share the tty rule with `cmd_ssh`.
- `sshx.guest_out(..., check=False)` turns an ssh exit 255 (the box is unreachable) into empty output at `disk_lines` and `luks_device_fstype` in `status.py` and `vm.py`, and at the two `df` reads of `cmd_disk_grow`. Each reads empty as "unreadable", which is mostly the right outcome, but the "is it up?" hint that `sshx.probe` raises on 255 is lost. Candidate fix: read those through `sshx.probe`.
- `proc.atomic_write` removes its temp file only on `Exception` (`yolobox_cli/proc.py`), so a Ctrl-C (`KeyboardInterrupt` is a `BaseException`) between `mkstemp` and `os.replace` leaves a stray temp file beside the target; in the instance directory or the state directory it is never cleaned. Candidate fix: `except BaseException`, as `create_volume` already does.
- The Python 3.9 unit leg in `.github/workflows/verify.yml` is pinned to `ubuntu-24.04`, because setup-python has no 3.9 build for ubuntu-latest's 26.04 image. The pin will age out when GitHub retires the 24.04 image. Then run the leg in a `python:3.9` container as a non-root user with `jq` and `gawk` installed (as root with those missing, 26 tests fail and 2 skip), or drop the floor along with the host's Xcode Python 3.9.
- CI evaluates less on the darwin side than on the Linux side. The `eval` job in `.github/workflows/verify.yml` runs on `ubuntu-latest` (x86_64): the podman log-driver check, the hardening-settings check, the egress `nft --check` and fixture-diff steps and the `lanAllow` rejection step all run against `YOLOBOX_HOST_OS=linux` on the x86_64 guest only, and the Mac box (`--system aarch64-linux`, `YOLOBOX_HOST_OS=darwin`) is evaluated only as far as its `drvPath`. A `hostOs == "darwin"` or aarch64 branch that renders badly (an egress file, a hardening value) would pass CI. Candidate fix: render the same checks from the darwin and aarch64 evaluations (the rule files are `builtins.toFile`, so they print without a builder), or at least diff the darwin render of the egress files against the fixtures.
- GitHub `environment: release` protection for HOMEBREW_TAP_TOKEN not configured.

## aws-broker

Both items are in `aws-broker` and predate the package split. See also the broker bullet under [Several machines](#several-machines).

- `reclaim_socket_path` probes the socket with a connect and unlinks it if nothing answers, and the bind happens later (`bind_server`). Between the probe and the bind a second broker can pass the same probe: A unlinks and binds, then B unlinks A's fresh socket file and binds its own. Both brokers run, A's socket has no name any more, and the guest's forward reaches only B. `yo` starts one broker at a time and holds no lock, so two concurrent `yo` runs on one machine can trigger it. Candidate fix: take an `flock` on a sibling `aws-broker.sock.lock` around reclaim and bind.
- `main()` installs the SIGTERM handler after `bind_server` and before `READY`, so a SIGTERM that arrives after the bind and before `signal.signal` (a replaced broker being stopped while it is still starting) takes the default action and leaves the socket file behind; the next start reclaims it as stale, so the damage is a window in which the path exists and nothing answers. Candidate fix: install the handler before the bind, with the identity recorded once the bind has happened.

# Security backlog

Open security items. Each one names its evidence and a candidate fix.

- Port-mirror squat (medium). Lima mirrors guest TCP ports 1024-49151 onto the host's `127.0.0.1`, minus the small deny-list in `lima/yolobox.yaml`. An agent can bind an in-range port before a host tool does, and a host connection to that `127.0.0.1` port then reaches the guest listener, so real bytes cross. Usually the squat only denies the port, because the host tool then fails to bind. But a browser that navigates to `localhost:PORT` for a dev or OAuth flow, whose real server never bound, would reach the guest. Candidate fixes: shrink the mirror range, extend the deny-list with known callback ports, or make the mirror opt-in per port. Reproduction: as the agent, bind `0.0.0.0:34567` in the guest, then on the host run `nc -z 127.0.0.1 34567`. With several boxes the same mirror makes their ports collide, see [Several machines](#several-machines); a Linux host has no such mirror (`docs/linux-host.md#host-ports`).
- The 1Password forward exposes every vault key (high blast radius, as designed). The forwarded agent serves every key in the vaults `agent.toml` names, because it filters by vault only. That includes the disk key (`yolobox-disk`) and any git or cloud keys in those vaults. `LUKS_SIGN_DATA` is public and the derivation is deterministic, so one approved `yolobox-disk` signature yields the disk passphrase. The per-sign 1Password prompt is the only gate. Candidate fix: a per-key or per-item filter, or a dedicated forwarded socket that exposes only what the box needs.
- Supply chain: the flake ref is a movable tag with no rev pin (high, as designed). `yo` builds from `github:aka-rider/yolobox/v<version>`. The release workflow force-moves that tag. `nixos-rebuild` runs as root in the guest and fetches the mutable tag, which also builds the initrd and the LUKS unlock. So an owner, token or tag compromise gives root in the guest and in the initrd on the next operator-initiated rebuild. The agent cannot trigger this, so it is trust-on-first-use. The harness installers are also unpinned `curl | bash`, which stays contained to the agent. Candidate fix: have the host pass a rev and narHash that the guest verifies, and checksum the installers.
