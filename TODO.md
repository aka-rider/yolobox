# Upstream

The reasoning is in lima/yolobox.md#an-empty-page-means-limas-forwarder-died. The lima side is done: lima-vm/lima#5557 was closed, PR #5558 merged, and the fix shipped in lima v2.2.1. What remains is the nixos-lima change below.

- nixos-lima PR [nixos-lima/nixos-lima#125](https://github.com/nixos-lima/nixos-lima/pull/125): `restartIfChanged = false` on `lima-init` and `lima-guestagent`, because a nixpkgs bump alone restarts them and, on lima v2.1.2 through v2.2.0, that triggers the dead-forward bug. Still open and unmerged.
  - Once it is merged and this flake's `nixos-lima` input is bumped, the flake's own `restartIfChanged = false` becomes redundant: remove it.
- lima: `limactl stop` (and the stop half of `limactl restart`) can hang on the `vz` driver, seen on lima 2.2.0 and 2.2.1, with no isolated trigger. Symptom: after about three minutes `did not receive an event with the "exiting" status`; the hostagent took SIGINT, stopped some forwards, and never exited, and a child `limactl hostagent` may spin at high CPU and outlive `limactl stop -f` of its parent. `lima_stop()` prints its recovery text. Recovery: `kill -9` the hostagent (and the spinning child); under vz that also ends the VM. A gentler route is `sudo systemctl reboot` inside the guest (`yo ssh sudo systemctl reboot`), though the child still needs `kill -9`.

# Known problems

- `yo cp` drops build output in the staging directory after scp has already transferred it, so pulling a tree with a large `node_modules` still moves those bytes (`drop_from_staging` in `yo`, `yo.md#downloads-never-land-build-output`). The fix is a transport that excludes on the guest side: tar with `--exclude` over ssh, or a guest-side listing that feeds scp the paths to fetch. scp has no exclude option. Such a change must keep the CONSTITUTION rules for `yo cp`: glob-escape every guest source and never a destination, stage beside the destination and plan the merge before anything moves, and keep the control-path skip. It must also keep `-p` (see `yo.md#yo-cp`), because `unlock_tree` and the landed directory modes depend on how scp -p shapes them; a tar transport would need `--same-permissions` semantics and the same unlock step.
- pi's LSP (pi-lens) finds basedpyright on PATH only. The box has no direnv, so a project's devbox is on pi's PATH only when pi runs inside `devbox shell`; pi started from a plain shell has no basedpyright. Check whether pi-lens can be given a launch command (then point it at `lspWrapper` in `nix/lsp.nix`), or whether herdr should start pi panes through `devbox run`.
- The throwaway-instance rescue for a box stuck in its initrd (a second lima instance with this instance's `disk` file attached) is untested. See `docs/disk-encryption.md#recognising-failures`.
- Verify on a live box that `yo ssh` drops when an exit node is selected without `--exit-node-allow-lan-access`. The flag itself is verified (see `nix/tailscale.md#exit-nodes`); the no-flag half is still only an expectation. Check on a box built without the flag: `yo ssh sudo tailscale set --exit-node=<node>`, then see whether `yo ssh` survives.
- `limactl stop` can hang on the vz driver; see the lima entry under Upstream.
- The swapfile size is unconditional (`swapDevices` in `nix/base.nix` is 16 GiB on every disk), and a full root disk shows up as a DNS failure instead of a disk error: `dhcpcd` gets ENOSPC, `/etc/resolv.conf` is left at 0 bytes, and `tailscale up` loops on "failed to resolve". `yo.md#several-machines` now states a 40 GiB floor, but nothing enforces it. Candidate fixes: a free-space check in `net-check` and `yo status` that names the full disk, and a swap size that a box's `/etc/yolobox/local.nix` can set (or that scales with the disk) without `lib.mkForce`.
- The Python 3.9 unit leg in `.github/workflows/verify.yml` is pinned to `ubuntu-24.04`, because setup-python has no 3.9 build for ubuntu-latest's 26.04 image. The pin will age out when GitHub retires the 24.04 image. Then run the leg in a `python:3.9` container as a non-root user with `jq` and `gawk` installed (as root with those missing, 26 tests fail and 2 skip), or drop the floor along with the host's Xcode Python 3.9.
- AF_VSOCK from the guest to the host (CID 2) is not seen by the egress table. Lima runs with `overVsock:false` and nothing listens host-side, so every connect to CID 2 is answered with a connection reset. Nothing is reachable today. This is an accepted residual (see `nix/egress.md#residuals`). A future host-side vsock listener would be entirely outside the table's reach.
- The box has no global IPv6. `enp0s1` has only an fe80 link-local address, there is no IPv6 default route, and only `tailscale0` carries a v6 address (a ULA). So Lima's NAT gives the box no global IPv6. The IPv6 form of the host-address hairpin is unreachable unless the host gains global v6 and Lima assigns the guest a global v6 default. See `nix/egress.md#residuals`.
- GitHub `environment: release` protection for HOMEBREW_TAP_TOKEN not configured.
- A box on a tailnet should have its ACL reviewed. `tailscale0` is trusted, so the ACL is the only access control: every node it admits reaches every port of the box (see `nix/tailscale.md#firewall`).
- tailscaled can log `new contact: peer=[...] via=derp` every few seconds for one peer. Open: possibly a peer that never gets a direct path.
- Immutable releases must stay off: release.yml force-moves the tag and re-uploads with --clobber.
- Secrets that still live on disk despite the constitution's rule: lima's instance ssh key (`~/.lima/_config/user`, lima owns it), the agent's vendor credentials (for example claude's and gh's credential files under the agent's home), and the stage-2 sshd host keys. Each is a vendor's own storage; the rule forbids this repo from adding to the list, and the LUKS root now covers the guest-side ones at rest.
- The local-checkout recipe in `yo.md#bootstrap---version` (`yo bootstrap --version /home/agent/Developer/yolobox`) was derived from `mirror()`, not run on a live box. `nixos-rebuild` runs as root and the pushed tree is owned by `agent`, so nix may refuse the git repo with "not owned by current user". Run it on a box before trusting the recipe; if nix refuses, the recipe needs a `safe.directory` entry or a different owner.
- Several machines (`yo -m NAME`, see `yo.md#several-machines`) share some host-global state. Each item below breaks, or is weaker, once two or more boxes run at once; nothing was changed for them:
  - The LUKS key is one 1Password item (`yolobox-disk`) and the passphrase derives from it alone, so every instance's disk opens with the same passphrase. Whoever holds it for one box holds it for all, and rotating it needs every disk re-keyed.
  - The AWS broker has one socket (`~/.local/state/yolobox/aws-broker.sock`) and one watched hostagent pid (`ensure_aws_broker`, `broker_needs_restart`). When two boxes are up, each `yo` run restarts the broker to watch its own box's hostagent, and stopping the watched box ends the broker, so the other box loses its AWS credentials until its next `yo` run. Only matters where `aws` is installed and has SSO profiles.
  - `yo link` always names the git remote `yolobox`. `yo link` for a second instance in a repo already linked to the first fails with "remote 'yolobox' points at ... which is not this VM" until the first remote is removed, so a repo can be linked to one box at a time.
  - `lima/yolobox.yaml` mirrors guest TCP ports 1024-49151 onto the host's 127.0.0.1, same number on both sides. Two running boxes that listen on the same port collide: the second hostagent cannot bind it and lima logs the failure while the first box keeps the port.
  - `nix/luks/yolobox-luks-migrate.sh` prints `ssh in as root on port 60022` (the constant from `nix/luks/facts.nix`) when it refuses an encryption for lack of space. On a non-default instance the real port is the one in its `ssh.localPort`. The yo-side messages already print the right one.
- Kernel bugs behind unprivileged user namespaces. The agent can `unshare -Urn`, become root of its own namespace and make the kernel autoload `nf_tables` and the net/sched modules, whose bugs have given root before (CVE-2024-1086, CVE-2023-32233, CVE-2022-2588). The box keeps user namespaces because the chromium sandbox, rootless podman and the nix build sandbox need them, and it keeps `nf_tables` because the firewall and podman's bridge networks sit on it. So today the only mitigation is a current kernel (`linuxPackages_latest` in `nix/base.nix`). Next step: the net/sched modules are idle unless a box configures traffic control, so try blocking `cls_*`, `act_*` and the other `sch_*` names, then run `tests/box-hardening-check.sh` and check tailscale and podman networking. The `nf_tables` half has no fix at the box level. See `nix/hardening.md#known-residual-the-surface-behind-user-namespaces`.
- `yo disk-grow` is not implemented for libvirt boxes (`LibvirtDriver.disk_ceiling_gib` and `grow_disk` raise). It needs `virsh vol-resize` while the domain is stopped, then the same `cryptsetup resize` and `resize2fs` steps `cmd_disk_grow` already runs.

- On a Linux host an unprivileged `yo` cannot verify that the egress table is loaded: `nft list table` needs root, so `check_libvirt_host` sees only `systemctl is-active yolobox-host.service`. An operator who deleted the table without stopping the unit (see `linux/host-setup.md#the-host-table`) leaves a unit that reads `active` and a host with no table. Candidate fix: a root-owned oneshot that writes the table's presence to a world-readable file, or a handle `yo` can read without privilege.
- On a Linux host the owner check before each passphrase send (`LibvirtDriver.verify_initrd_listener`) is not atomic with the ssh connect, and a port with no listener passes it. A local process that binds the box's loopback port in that gap would receive the answer to the initrd's ssh handshake. The port sits above the kernel's ephemeral range, so only a deliberate squat can do it. Candidate fix: have ssh connect through a descriptor `yo` verified with `SO_PEERCRED`-style checks, or pin the initrd's host key through the domain.
- The Lima path has not been run live since `yo` was split into a Lima and a libvirt driver. The split is a refactor with the whole unit suite green on a Linux CI host, but `limactl`, vz, the port mirror and the reverse forwards were last exercised on a Mac before it. Run `yo up`, `yo status`, `yo bootstrap` and `tests/box-hardening-e2e.sh` against a throwaway instance on a Mac before the next release.
- `yo` has no command to delete an instance. A libvirt box is removed by hand: `virsh -c qemu:///system destroy yolobox-NAME`, `undefine yolobox-NAME --nvram`, `vol-delete yolobox-NAME.qcow2 default` and `vol-delete yolobox-NAME-cidata.iso default`, then `rm -r ~/.local/state/yolobox/instances/NAME`. A Lima box is removed with `limactl delete`. A `yo delete` would need to refuse a running box and print what it removes.
- A box on a Linux host with global IPv6 has a global address, where a Mac box has none (`docs/linux-host.md#ipv6`). Both egress tables reject the same v6 ranges, but a LAN machine with a global address cannot be told from the internet. Candidate fix: give the domain no IPv6 (passt `--ipv4-only`, if libvirt exposes it) and say so in the story.
- The polkit rule `host-setup.sh` installs lets the operator's host processes manage `qemu:///system`, which is root-equivalent (they can define a domain that passes a host device through). Accepted because the operator is already in `wheel`; see `docs/linux-host.md#polkit`. Candidate fix: a rule limited to the actions `yo` uses, if libvirt's polkit actions can be made fine enough.
- `/run/libvirt/qemu/passt` has no sticky bit, and `host-setup.sh` step (j) gives `yolobox-vm` write access to it by ACL. A compromised yolobox passt or QEMU, which runs as `yolobox-vm`, could unlink the passt sockets of other, non-yolobox domains in that directory. That disrupts their networking; it does not reach into them. Alternative considered and rejected: run every host VM as `yolobox-vm`, which changes foreign VMs.
- A box on the same tailnet as a Linux host can connect to the host's tailnet address, and to its sshd on `0.0.0.0:22`, because the guest accepts everything out of `tailscale0`. The agent holds the forwarded 1Password agent, so a served key that is in the host's `authorized_keys` would let it log in. Mitigation is on the host: bind sshd away from `tailscale0` and keep the tailnet policy from granting boxes the host. `tests/box-libvirt-check.sh` prints `RESIDUAL tailnet-host-ssh`. See `docs/linux-host.md#the-tailnet-residual`.

# Security backlog

Open security items. Each one names its evidence and a candidate fix.

- Port-mirror squat (medium). Lima mirrors guest TCP ports 1024-49151 onto the host's `127.0.0.1`, minus the small deny-list in `lima/yolobox.yaml`. An agent can bind an in-range port before a host tool does, and a host connection to that `127.0.0.1` port then reaches the guest listener, so real bytes cross. Usually the squat only denies the port, because the host tool then fails to bind. But a browser that navigates to `localhost:PORT` for a dev or OAuth flow, whose real server never bound, would reach the guest. Candidate fixes: shrink the mirror range, extend the deny-list with known callback ports, or make the mirror opt-in per port. Reproduction: as the agent, bind `0.0.0.0:34567` in the guest, then on the host run `nc -z 127.0.0.1 34567`.
- AWS broker slot exhaustion (low to medium). `aws-broker` caps concurrency at 32 slots with a `BoundedSemaphore`. Its per-connection timeout is a per-recv socket timeout, which resets on every byte, so it is not a wall-clock deadline. A client that trickles bytes holds a slot indefinitely, and 32 such clients deny the broker. One broker serves every running box, so with several boxes one can starve another's AWS credentials. The damage is bounded, because any `yo` run restarts the broker and clears the slots. No secret leaks on the error paths, since the broker requires a SessionToken. Fix: a total wall-clock deadline per request.
- `yo cp` overwrites ordinary existing files during a merge, which is the documented "pull my work back" behavior. The control paths (`.git`, `.hg`, `.svn`, `.envrc`, `.vscode`, `.idea`) are never landed. Anyone who pulls a guest tree onto an existing tree should still review it, because the pull is already the sandbox trust boundary (see `CONSTITUTION.md`).
- The 1Password forward exposes every vault key (high blast radius, as designed). The forwarded agent serves every key in the vaults `agent.toml` names, because it filters by vault only. That includes the disk key (`yolobox-disk`) and any git or cloud keys in those vaults. `LUKS_SIGN_DATA` is public and the derivation is deterministic, so one approved `yolobox-disk` signature yields the disk passphrase. The per-sign 1Password prompt is the only gate. Candidate fix: a per-key or per-item filter, or a dedicated forwarded socket that exposes only what the box needs.
- Supply chain: the flake ref is a movable tag with no rev pin (high, as designed). `yo` builds from `github:aka-rider/yolobox/v<version>`. The release workflow force-moves that tag. `nixos-rebuild` runs as root in the guest and fetches the mutable tag, which also builds the initrd and the LUKS unlock. So an owner, token or tag compromise gives root in the guest and in the initrd on the next operator-initiated rebuild. The agent cannot trigger this, so it is trust-on-first-use. The harness installers are also unpinned `curl | bash`, which stays contained to the agent. Candidate fix: have the host pass a rev and narHash that the guest verifies, and checksum the installers.
