# nix/base.nix: the stories behind its settings

`nix/base.nix` carries the short reason beside each setting. This file keeps the incidents and the ways to recognise them. It covers the boot partition, debugger access, memory pressure, disk growth, IP forwarding and the sudo wrapper. Two accounts, locked passwords and the journal group are in [docs/accounts.md](../docs/accounts.md#two-accounts). The disk-full incidents are in [docs/disk.md](../docs/disk.md).

## The ESP holds one kernel

`/boot` is the EFI partition itself, `/dev/vda1`, 249 MiB (260,796,416 bytes). It is mounted there to match the shipped nixos-lima image, so a fresh instance never needs a mount migration. The ESP stays unencrypted, because GRUB reads the kernel from it before anything can be unlocked (see [docs/disk-encryption.md](../docs/disk-encryption.md#what-is-encrypted-and-what-is-not)). The initrd that unlocks the root disk lives there too, and it makes the kernel set larger; check `df /boot` after the switch that first carries it. The size is baked into the prebuilt image and cannot be grown. vda1 ends at sector 526335 and vda2 starts at 526336, the very next sector, so there is no gap to grow into.

A kernel set is about 92 MiB, and `linuxPackages_latest` brings a new one every few weeks. Two sets fit; three never do. The count that matters is not the retained one. `install-grub.pl` copies every retained generation's kernel into `/boot/kernels` first and unlinks obsolete files only after the `grub.cfg` rename. So the peak during a switch is the retained sets plus every set already there. With `configurationLimit = 2` the next kernel bump holds three sets transiently and dies mid-copy. With `1` the peak is about 198 MB against 260.8 MB.

Lowering the limit frees nothing on the switch that applies it, because pruning runs last. One more switch without a kernel change drains the old set. After that second switch `df /boot` shows the used bytes fall to one kernel set.

The failure surfaces late and lies. The closure builds, the profile advances, and only then does the bootloader install die with `No space left on device`. The box keeps running the old generation while `/nix/var/nix/profiles/system` claims the new one. So `readlink /nix/var/nix/profiles/system` and `readlink /run/current-system` disagree, and a reboot comes back on the old one. If the switch was piped through `tail`, the shell reports exit 0. Check `df /boot` first when a switch behaves strangely.

That readlink pair is also what `yo bootstrap` compares to decide whether to reboot (see [docs/distribution.md](../docs/distribution.md#bootstrap-reboot-decision)), and what `nix/guest/yolobox-guest.sh` compares before `nix-collect-garbage -d`, which would delete the running generation after a half-failed switch (see [nix/guest/yolobox-guest.md](guest/yolobox-guest.md#gc-tiers)).

The trade is that no rollback generation survives a kernel bump. That is acceptable, because the VM is rebuildable from this repo.

`/boot` stays on its own partition and is not moved onto the root filesystem. That would give unlimited space, but it would make `nix/base.nix` diverge from the image, so every fresh instance would need a manual mount migration before its first switch.

## Sysctl keys the kernel lacks

`systemd-sysctl` logged `Couldn't write '1' to 'kernel/unprivileged_userns_clone'` on every boot. The key is not ours and not podman's: `lima-init.nix` in nixos-lima sets `kernel.unprivileged_userns_clone = 1`, a knob that only the removed `-hardened` kernels had. Mainline (`boot.kernelPackages = pkgs.linuxPackages_latest`) has no such file, so the write failed and was only a warning. nixpkgs removed its own `security.unprivilegedUsernsClone` option for the same reason, so there is nothing to turn off there. `nix/base.nix` sets the key to `lib.mkForce null`, which NixOS drops when it renders `/etc/sysctl.d/60-nixos.conf`.

Unprivileged user namespaces are not affected. A mainline kernel allows them by default, bounded by `user.max_user_namespaces`, which the chromium sandbox, rootless podman and the nix build sandbox rely on (see [hardening.md](hardening.md#sysctls)). Recognise a regression by that warning coming back in `journalctl -b -u systemd-sysctl`, or by `unprivileged_userns_clone` appearing in the rendered file (`.github/workflows/verify.yml` checks it).

## Same-uid ptrace

`py-spy dump --pid N` against an already-running agent process died with permission denied. Nothing in the repo set ptrace, so the kernel's Yama default applied: `kernel.yama.ptrace_scope = 1`. That lets a process ptrace only its own descendants, or a process that declared the tracer through `prctl(PR_SET_PTRACER)`, which py-spy cannot arrange from outside. That is why `py-spy record -- python app.py` worked all along (the target is py-spy's child) and attaching to a server started elsewhere did not.

`nix/base.nix` now sets `boot.kernel.sysctl."kernel.yama.ptrace_scope" = 0`. NixOS renders it into `/etc/sysctl.d/60-nixos.conf`, and `systemd-sysctl` carries that file in its restartTriggers, so a `switch` applies it with no reboot.

It is safe because the box's boundary is the uid split (see [docs/accounts.md](../docs/accounts.md#two-accounts)), and Yama does not touch that. The kernel's classic check in `__ptrace_may_access` runs at every scope. It requires the tracer's ids to match the target's real, effective and saved ids, or `CAP_SYS_PTRACE` in the target's user namespace. So at scope 0 the agent (uid 1000) can attach to its own processes (python servers, other claude sessions, herdr). It still cannot attach to the operator's (`systemd-socket-proxyd` for 1Password and the AWS broker, the `sshd-session` holding the reverse forwards) or to root's. What scope 1 protected was one agent-uid process from another, and the agent already owns that uid entirely. It can rewrite `~/.zshrc`, set `LD_PRELOAD`, replace binaries under `~/.local`, and read every secret those processes hold on disk.

The tempting alternative is forbidden by `CONSTITUTION.md`: a `security.wrappers` entry or `setcap` giving py-spy or gdb `cap_sys_ptrace`. That capability bypasses the uid comparison, so the agent could attach to a root process and become root. The only file capabilities on the box today are podman's `newuidmap` and `newgidmap`.

A rootless container is a separate case that scope 0 does not fix. Its processes run under subuids (for example a postgres container's data uid), which are a different uid to the kernel, so a plain attach is refused at any scope. `podman unshare py-spy dump --pid <host pid>` works. Inside `podman unshare` the agent is root of the rootless user namespace, which holds `CAP_SYS_PTRACE` over every process in it and its children, and it keeps the host pid namespace, so host pids apply. Run it from the agent's home, because `podman unshare` fails to chdir into an unreadable cwd. `podman exec` with py-spy inside the container works too.

Recognise a regression by `sysctl kernel.yama.ptrace_scope` printing `1` again. Two other causes of the same permission denied are not this one: a non-dumpable target (a setuid exec, `PR_SET_DUMPABLE 0`, a credential change after start) and a target with file capabilities the tracer lacks. `strace` is on the box-wide PATH. py-spy and gdb are not; they come from a project's devbox or venv.

## Memory pressure

Without swap, memory pressure goes straight to the kernel's global OOM killer with no warning stage. A `nixos-rebuild switch` on a box already low on available memory can tip it over. Symptom: every rootless container dies with exit 137 during the switch. The journal shows the kernel killer, not `systemd-oomd`, picking browser and application worker processes first, and eventually the uid-501 user manager: `user@501.service` fails with result `signal`. The agents themselves survive, because ssh session scopes hang off `user.slice` directly, not under `user@.service`. So the blast radius of a user-manager kill is exactly the rootless containers.

Two changes address the two halves. `nix/swap.nix` declares a `/var/swapfile` of `yolobox.swapSizeMiB` MiB, 16 GiB by default, so reclaim has somewhere to go before the killer runs, and `lima/yolobox.yaml` sets the box to 16 GiB and 8 cpus. Then systemd's upstream `user@.service` ships `OOMScoreAdjust=100` (verified with `systemctl show user@1000.service -p OOMScoreAdjust`), which makes the per-user manager a preferred victim over every system service at 0. A drop-in (`overrideStrategy = "asDropin"`, so upstream's unit text is kept, not replaced) sets it to -500. Podman sets its own `oom_score_adj` on containers (200), so they stay individually killable. What the drop-in changes is that the kernel takes one container worker, or the agent's own link job, before it takes the manager that holds all of them.

The swapfile is allocated in full on the root disk, and a full root disk breaks name resolution (see [docs/disk.md](../docs/disk.md#a-full-disk-looks-like-a-dns-failure)). A box with a small disk sets `yolobox.swapSizeMiB = 4096;` in its `/etc/yolobox/local.nix`, with no `mkForce`, and `0` declares no swap at all. NixOS's `mkswap-var-swapfile` unit recreates the file when its size differs from the configured one, so a switch applies a new size. With `0` the unit no longer exists and the old `/var/swapfile` stays on the disk, unused, until it is deleted by hand.

## Pushing into a VM checkout

Code reaches the VM by `git push` into a checkout there, over a remote the operator adds by hand (the ssh host is `lima-yolobox`, or `lima-<name>` for an instance). Nothing in `yo` sets the remote up, so `programs.git.config` in `nix/base.nix` sets `receive.denyCurrentBranch = "updateInstead"` system-wide, and every repo in the VM accepts a push to its checked-out branch. Git applies it by updating the worktree, and refuses the push when the worktree or index differs from HEAD, so nothing uncommitted is overwritten.

Two things follow. A VM checkout that was dirtied (a deleted tracked directory, an agent's half-finished edit) refuses every later push, with an error that does not point back at the cause. That is why `yolobox-guest gc` removes only git-ignored directories. Second, the VM commits `devbox.lock` itself, so its branch moves ahead of the Mac's, and a push from a Mac that has not pulled lands on a diverged branch and is refused. Pull first.

The pull is also where the sandbox's trust boundary sits. The agent can write to the VM checkout, so the commits it authored there are untrusted input the moment they reach the Mac, where the operator builds and runs them. Review them before running anything.

Recognise the setting being lost by `git push` answering `refusing to update checked out branch`.

## Growing the root disk

`~/.lima/yolobox/disk` is sparse. It reads as the declared ceiling and allocates only what the guest wrote. `lima/yolobox.yaml` declares `disk: 100GiB`, which is the ceiling at creation, and `yo disk-grow` raises it later. The guest mounts `/` with `discard` and `fstrim.timer` runs weekly, so freed blocks are punched back out of the host file. Over-declaring the ceiling costs nothing, which is the intended use.

Raising the ceiling takes three steps, and each one does a different thing. The host step is `limactl edit yolobox --disk <GiB>`, grow-only, with the instance stopped. The partition step is `boot.growPartition = true` in `nix/base.nix`: a `growpart` unit that grows the partition, vda2, to fill the disk on every boot. Its `SuccessExitStatus = "0 1"` makes an already-grown boot a harmless no-op. Its stock script derives the partition from `readlink -f` of `fileSystems."/".device`, which is `/dev/dm-0` now that the root is a mapper device, so `nix/luks.nix` replaces the script with `growpart /dev/vda 2`. The last step is the LUKS mapping and the filesystem on it, and `yo disk-grow` runs it with the passphrase only `yo` holds: `cryptsetup resize --key-file - root`, then `resize2fs /dev/mapper/root`, after the VM is back up. `fileSystems."/".autoResize` is off because it renders `x-systemd.growfs`, and `systemd-growfs` cannot resize a keyring-keyed LUKS2 mapping. The whole design is in [docs/disk-encryption.md](../docs/disk-encryption.md#growing-an-encrypted-disk).

Skipping the partition step is silent. The backing file grows, the guest boots clean, `df` is unchanged, and nothing logs. `systemctl show -p LoadState --value growpart` must answer `loaded`; `not-found` means the running generation cannot grow anything. `growpart` only runs on a boot whose generation carries the option, so the switch must land before the resize. `yo disk-grow` checks this before touching anything. A missing partition step goes unnoticed on a fresh instance, because the shipped nixos-lima image grows vda2 itself at first boot, before our config takes over.

## NAT and IP forwarding

nixos-lima's `lima-init.nix` sets `networking.nat.enable = true`, and nixpkgs' nat module turns that into `net.ipv4.ip_forward=1`. That makes the guest a router, so a packet from the host side could cross the guest into the tailnet. `nix/base.nix` turns NAT off with `mkForce`. Nothing in the box routes for others: rootless podman uses pasta, and tailscale runs only as a client, so no feature needs forwarding. The check is `yo ssh sysctl -n net.ipv4.ip_forward`, which must print `0`.

## sudo is wheel-only

`nix/base.nix` sets `security.sudo.execWheelOnly = true`. It drops other-execute from the setuid `sudo` wrapper, so the agent, which is not in `wheel`, cannot exec it at all. The agent could not authenticate anyway, because its password is locked and it is in no sudoers rule. But a setuid root binary that anyone can run is attack surface, and the wrapper should not be reachable by the account that has no use for it. The box also has no direnv (see [nix/lsp.md](lsp.md#no-direnv)). The check is `ls -l /run/wrappers/bin/sudo`, which must show no `x` for others, and `sudo -n true` as the agent must fail with permission denied, not with a password prompt.

## No host OS in the guest

The same box runs under two hypervisor stacks: Lima/vz on a Mac and libvirt on a Linux PC. A few settings must differ between them. The guest is never told which stack runs it, because the host OS is only a proxy for the facts those settings need, and a proxy goes wrong at the edges: an x86_64 box runs under Lima on an Intel Mac and under libvirt on a Linux PC. A box that was told its host OS also needed `yo` to pass it on every rebuild, and a hand rebuild that guessed it wrong silently changed the box. So each setting gates on the fact it needs, and `TestTheGuestNeverLearnsTheHostOs` fails if `YOLOBOX_HOST_OS`, `hostOs` or `host-os` appears in `flake.nix` or anywhere under `nix/`. An older `yo` still passes `YOLOBOX_HOST_OS`; the flake never reads it, and CI's eval job proves the box is the same derivation whatever it says.

- **`lima-guestagent` gates on its binary.** nixos-lima's unit script runs `lima-guestagent daemon` from the cidata disk, which nixos-lima mounts at `/mnt/lima-cidata`. Lima puts that binary on the cidata disk it builds; the cidata `yo` writes for a libvirt domain has none. So the unit carries `ConditionPathExists=/mnt/lima-cidata/lima-guestagent`: it runs on a Lima box and is skipped, not failed, on a libvirt one. CI checks the unit's script still names that path, which catches a nixos-lima bump that moves the binary. `tests/box-hardening-check.sh` checks the unit is active when the binary exists and has `ConditionResult=no` when it does not. `restartIfChanged = false` stays on the unit either way.
- **Rosetta gates on the guest's CPU.** Rosetta is a vz feature of Apple silicon, and an aarch64 guest runs only there: vz cannot emulate, so an Intel Mac's guest is x86_64, and the libvirt driver runs only x86_64 guests. So `virtualisation.rosetta` is on exactly when `pkgs.stdenv.hostPlatform.isAarch64`. `nofail` on the mount was considered and rejected: it takes the mount out of `local-fs.target` ordering, and `systemd-binfmt` then races it and registers nothing. An aarch64 libvirt guest would wait on a share that never comes, so supporting one needs a gate of its own (TODO.md).
- **The operator's `AllowUsers` holds on every box.** On a Linux host the operator's key is served by the host's 1Password agent, which the agent account reaches through the forwarded socket, so the agent could log in to its own box as the operator. `AllowUsers = [ "${username}@192.168.5.2" agentUser ]` admits the operator only from the gateway address the host's forwarded ssh port arrives from, and the agent from anywhere. A firewall rule drops packets that claim that source on any interface but `enp0s1`, so the agent cannot fake the address over loopback. Both rules cost a Mac box nothing (its operator key is a file under `~/.lima`, which the agent never sees, so they guard nothing there today), so they apply everywhere instead of being gated. A vsock peer has no IP address, so the rules also depend on `ssh.overVsock: false`, and `yo up` refuses an instance without that pin (`LIMA_FATAL_GAPS`). The full Linux story is in [docs/linux-host.md](../docs/linux-host.md#the-operators-key).

The CPU is the one fact the box varies on, and it is the system of the nix that evaluates: an Apple silicon Mac's box is `aarch64-linux`, and an Intel Mac's box and a Linux PC's box are `x86_64-linux`.

Recognise a regression: a libvirt box whose `systemctl --failed` lists `lima-guestagent` lost the condition; an Apple-silicon box where `cat /proc/sys/fs/binfmt_misc/rosetta` fails lost the CPU gate; and `ssh` as the operator refused with `Permission denied` on a Mac box means its ssh no longer arrives from 192.168.5.2 (`echo $SSH_CONNECTION` inside the box names the source).

## sshd penalties

OpenSSH 10 penalises a source address for failed logins (`PerSourcePenalties`; the box's `sshd -T` prints `authfail:5 noauth:1 invaliduser:5 min:15 max:600`). Once a source has run up 15 s of penalties, sshd drops every new connection from it. On this box every connection from the host arrives from one address, the gateway 192.168.5.2: passt delivers libvirt's forwarded port from there, and Lima's usernet does the same. So the penalty can only ever lock out the host, with every `yo` command at once.

It happened on a libvirt box. The host's 1Password agent died in an app update, so the operator's stage-2 login failed on the client side (`Connection closed by authenticating user ... [preauth]`). `boot_stage()` then fell back to logging in as `root` to look for the initrd. Stage 2 logged `User root from 192.168.5.2 not allowed because not listed in AllowUsers`, then `srclimit_penalise: 192.168.5.2/32: activating ipv4 penalty ... invalid user`, then `drop connection ... penalty`. For the next 15 to 20 s every `yo` command got `kex_exchange_identification: Connection reset by peer`, and `yo status` said `unreachable — is it up?`.

Three changes close it:

- `PerSourcePenaltyExemptList = "192.168.5.2"`. Penalising the gateway can only lock out the host, and the host is the operator. The trade is that sshd no longer slows down a brute-force attempt coming from the host side. That costs little: every login is by key (`PasswordAuthentication` and `KbdInteractiveAuthentication` are off), and the anti-spoof rule above drops anything claiming 192.168.5.2 on any interface but `enp0s1`, so the agent inside the box cannot borrow the exemption. Other sources keep the default penalties, including the tailnet, whose addresses are 100.64.0.0/10. `TestStage2SshdIsToldApartWithoutALogin` keeps the exempt address equal to the one in `AllowUsers`.
- `VersionAddendum = "yolobox-stage2"`. The stage-2 sshd's banner says what it is, so `yo` tells it from the initrd's sshd without logging in, and it never offers stage 2 a `root` login (see [docs/disk-encryption.md](../docs/disk-encryption.md#how-yo-reaches-the-initrd)). The initrd's sshd copies only a few of stage 2's settings (KexAlgorithms, Ciphers, MACs, LogLevel, UseDns), and CI checks its rendered `sshd_config` carries no mark.
- On a Linux host, a command that must log in first checks that the 1Password agent offers the operator's key (`Driver.require_login_key`, run by `main()`). A dead or empty agent is named as such, and that command sends sshd no doomed login. `yo down` and `yo status` need no login and go on without it ([docs/linux-host.md](../docs/linux-host.md#the-operators-key)).

Recognise it: every `yo` command fails with `kex_exchange_identification: Connection reset by peer` for a few seconds to minutes, `yo status` says `unreachable`, and `journalctl -u sshd` in the box shows `activating ipv4 penalty` for 192.168.5.2. On a box built before the exemption, wait out the penalty (at most 600 s); then rebuild.

## Hostname

`networking.hostName` is the `hostname` that `flake.nix` threads in, from the optional `YOLOBOX_HOSTNAME` (default `yolobox`, one lowercase DNS label, see [docs/distribution.md](../docs/distribution.md#nix-flake-check-throws-with-no-explanation)). `yo` passes `yolobox` for the default machine and `yolobox-<name>` for `-m <name>`, so two boxes on one tailnet do not fight over the node name `yolobox`. The same name goes to `tailscale set --hostname` (see [nix/tailscale.md](tailscale.md)). A manual `nixos-rebuild` of a named machine without `YOLOBOX_HOSTNAME` renames the box back to `yolobox`; `rebuild_hint()` prints the variable for that reason. The box stamps its hostname into `/etc/yolobox/hostname`, and `yolobox-guest rebuild switch`, the rebuild to run inside the box, reads it from there (see [nix/guest/yolobox-guest.md](guest/yolobox-guest.md#rebuild)).
