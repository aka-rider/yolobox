# t3code

The code is `nix/t3.nix`. t3code is not a nix package. It installs and updates itself from its vendor, the same as claude and pi, and the box owns only its environment.

## Vendor install and drop-in

`yolobox-harness-install` (see [Install phases](harnesses.md#install-phases)) runs `curl -fsSL https://t3.codes/install.sh | bash` when `~/.local/bin/t3` is absent. The installer never edits an rc file. The script then runs `t3 service install` once, when `~/.config/systemd/user/t3code.service` does not yet exist. That vendor command writes the real unit: `ExecStart` pointing at the version the installer just unpacked under `~/.t3/runtime/versions/<version>/`, `WorkingDirectory=%h`, and both `StandardOutput` and `StandardError` appending to `~/.t3/userdata/logs/boot-service.log`. `t3 update -y`, run by hand or from t3's web UI, downloads a new version the same way and rewrites that same unit file. A vendor update is therefore welcome, the same guarantee claude's launcher relies on for `claude update`.

`nix/t3.nix` owns only a drop-in on top of that unit. `systemd.user.services.t3code` with `overrideStrategy = "asDropin"` writes just `/etc/systemd/user/t3code.service.d/overrides.conf`. No unit file of that name exists in the nix store, so systemd finds the vendor's file under `~/.config/systemd/user` and merges the drop-in onto it. This is the same trick as the `user@.service` override in [Memory pressure](base.md#memory-pressure). Verify it with `systemctl --user cat t3code.service` as the agent, which prints the vendor unit first and the drop-in second.

The drop-in pins `T3CODE_HOST=127.0.0.1` and `T3CODE_PORT=3773`. It carries the agent's environment from `nix/lib/agent-env.nix` and `NIX_LD` and `NIX_LD_LIBRARY_PATH` from `nix/lib/nix-ld-env.nix`, because t3's binary is a dynamically linked glibc ELF and nix-ld lets it run unpatched. Its `path` puts `~/.local` ahead of `/run/current-system/sw`, so a t3-spawned claude goes through the box's launcher and picks up `HERDR_AGENT` and the Playwright settings file. The drop-in has `ConditionUser` and no `wantedBy`, so it never enables or starts the unit. The vendor's `t3 service install` did that, and re-enabling it on update is t3's job.

`t3 serve`'s `$HOME` must equal an interactive session's. `t3 pair` finds the server through `$HOME/.t3/*/server-runtime.json`, and a mismatch makes `yo t3` say "No running T3 Code server found" while the unit is active. The drop-in's `environment.HOME` keeps that true.

## Service status

The unit is a user unit, so it lives in the agent's manager, not the system one. `journalctl -u t3code` without `--user`, and `systemctl show -p ActiveState t3` as the operator, answer nothing at all: an empty load state, not an error. `yo` asks the agent instead. `t3_require_service()` runs `systemctl --user show -p LoadState -p ActiveState --value t3code.service` over `ssh_run(AGENT, ...)`. That needs no pty and no login shell, because the agent lingers (see [Lingering](harnesses.md#lingering)). logind pre-creates `/run/user/1000` at boot, and sshd's PAM stack sets `XDG_RUNTIME_DIR` on every connection, interactive or not.

`t3_require_service()` tells three failure shapes apart:

- No answer at all means the agent account is unreachable. Run `yo status`.
- A `LoadState` other than `loaded` means t3 was never installed as a service for this agent. Restart the install unit with `yo ssh sudo -u agent XDG_RUNTIME_DIR=/run/user/1000 systemctl --user restart yolobox-harness-install`.
- An `ActiveState` other than `active` is diagnosed with `journalctl --user -u t3code` as the agent, or by tailing `~/.t3/userdata/logs/boot-service.log`. It is the same output either way, because the unit's own log redirection captures t3's output.

`t3_require_service()` and the `t3:` line of `yo status` share two helpers, `t3_unit_state()` and `t3_service_problem()`, so they cannot disagree about what counts as broken.

That matters because a vendor update can break the unit with no error. `t3 update -y` (0.0.42 to 0.0.44, 2026-10-01) printed "Background service restarted". Then t3code.service crash-looped on `[service-launcher] Service state is invalid or unsupported.` until systemd's start limit hit, and it stayed failed for about 80 minutes. A stale `~/.t3/runtime/.service-stopping` marker had survived the update. `t3 service restart` does not clear it. `systemctl --user reset-failed t3code.service && t3 service install` does. Nothing watched the unit then. `yo status` does now, and when the unit is `failed`, the message from `t3_service_problem()` (on the `t3:` line, and from `yo t3` and `yo pair`) names that recovery.

## Version prune

Nothing prunes `~/.t3/runtime/versions/` on its own. install.sh and `t3 update -y` leave every version they downloaded behind, about 200 MB each. `yolobox-t3-prune` in `nix/t3.nix` is a `systemd.user.paths` unit that watches the directory, the same way `yolobox-claude-launcher` watches claude's store. It keeps the two newest and never deletes the version `~/.local/bin/t3` resolves to. The rank-then-settle order is explained in [The version keeper](harnesses.md#the-version-keeper). It applies here unchanged: settling first leaves three versions standing whenever the newest is too fresh to be a candidate.

Two details are specific to t3. "Resolves to" is a prefix match, not an equality. The script runs `readlink -f` on the link and spares any version directory that is a path prefix of the answer, because the binary sits several levels inside its version directory. An equality against its `dirname` matched the wrong level and would have deleted the running version. And a version in flight is never a target for a structural reason, beyond the 10-minute settle window. install.sh stages a download under a hidden `.staging-XXXXXX` name and `mv`s it atomically to its real name only after the archive is verified, extracted and carrying `.install-complete`. The prune's `find` excludes dotdirs, so every directory it can see is a completed install.

## Pairing

A bare URL fails auth. `t3 serve` prints a pairing URL in `journalctl --user -u t3code`, and `t3 pair` mints one. `t3 pair` builds the URL from the `--host` the server started with, `127.0.0.1`, which is useless elsewhere and has no override. Only `t3 auth pairing create --base-url` takes one. That is why `yo pair` is a separate command: it defaults to `http://<LocalHostName>.local:3773` and prints the URL instead of opening it.

`yo t3` opens a URL on the Mac, and that URL is text the guest produced. The checks that keep it from opening anything but loopback are in [Opening a guest URL](../yo.md#opening-a-guest-url). Pairing runs client to server only. No server-to-server pairing exists.

## Log noise

`Grok CLI health check failed` means there is no grok binary, which is expected. `Failed to flush telemetry` repeats every second when the endpoint is unreachable, which is also expected. A "not supported on this platform" message about the `linux-arm64` resource-monitor binary should no longer appear. The vendor's release ships that binary now, and it runs unpatched under nix-ld like `t3` itself. Its absence from `journalctl --user -u t3code` across a full restart was verified, though the journal carried no "monitoring started" line to confirm the positive case.
