# yo

Notes on the parts of `yo`, the host-side CLI, whose reasons are not obvious from reading the code. A short "why" lives in the code comment next to each piece. This file keeps the incidents, the evidence and how to recognise each failure. `yo --help`, `yo help` and `yo <command> --help` say what the commands do.

## Package layout

`yo` is a launcher: it puts its own directory on `sys.path`, imports `yolobox_cli.cli` and calls `cli.entry(argv)`, which turns a `YoError` into a message and an exit code. The code is the `yolobox_cli/` package, stdlib only and Python 3.9, one module per concern and acyclic from the bottom: `common`, `config`, `driver` and `ui` are leaves, then `state`, `proc`, `agent`, `sshconfig`, `sshx`, `release`, `guest`, `aws`, `forwards`, `unlock`, then the drivers `lima` and `libvirt` and the command modules `paths`, `status`, `vm`, `cp`, `session`, and `cli` on top. `common` is also what `aws-broker` imports, so it imports nothing else from the package. `config.SCRIPT_DIR` is the directory above the package, where `aws-broker`, `lima/` and `libvirt/` sit.

Modules import each other with relative imports and call `module.attr`, never a copy of a function (`proc.run(...)`, `state.driver()`). `from .x import NAME` is for classes and for constants nothing patches. That is the patch convention: a test patches the one global the code reads, `mock.patch.object(yo.proc, "run")`, and a name imported by name would be a second copy the patch misses. The test loader (`load_yo` in `tests/test_yo.py`) returns a namespace that reads any name from the module defining it, refuses two modules defining one name differently, and refuses writes. `tests/test_consistency.py` enforces both conventions.

The drivers are platform files. `cli.driver_for` imports `lima` on macOS and `libvirt` on Linux, and nothing else imports either, so brew ships no `libvirt.py` and the Linux nix package no `lima.py`. The libvirt driver is two files: `libvirt.py` (the `LibvirtDriver`: stop, start, ports, volumes, cidata, seed) and `libvirt_host.py` (the host preflight, and the policy a domain's XML is checked against: the allowlists and `domain_gaps`). Only `libvirt.py` imports `libvirt_host`, and `libvirt_host` ships exactly where `libvirt` does. Each platform's other files go the same way (see [distribution](docs/distribution.md#each-platform-ships-its-own-files)).

## The mirror

`yo enter`, `yo code` and `yo zed` land in the guest twin of the Mac's logical `$PWD`. That is the path relative to the Mac `$HOME`, grafted onto the guest `$HOME`, subdirectory included. Logical means `$PWD` as the shell spells it. A symlinked spelling is mirrored, never resolved, so the guest sees whatever name you `cd` through on the Mac.

The mapping is done by `mirror()`, which matches the Mac `$HOME` both as spelled and as `realpath($HOME)`. A `$HOME` reached through a symlink (macOS's `/var` is `/private/var`) comes back resolved from `os.getcwd()` whenever the shell reported no usable `$PWD`, and a cwd under it would otherwise match no prefix and land at the guest home with a missing-path note. Only the prefix is matched against the two spellings; the rest of the path stays as the shell spelled it. The guest path it produces then goes through `guest_path()`, which is why no `yo` command can target a guest path outside the guest `$HOME`. The one exception is `yo cp`, which also accepts an absolute path under `/tmp` (see "yo cp" below).

When the mirrored path does not exist in the VM, the session lands at the deepest existing ancestor. When the Mac cwd is outside `$HOME`, it lands at the guest home. Both cases print `MISSING_PATH_NOTE` to stderr: `path "%s" does not exist in the yolobox you are in "%s"`. `yo bootstrap` needs no mirrored path, because it builds the VM straight from a flake ref and there is nothing of yolobox's own to locate inside the guest.

## yo cp

### Why scp, not `limactl cp`

`limactl cp` cannot move a file into a project the agent then has to write to. It copies as the operator (uid 501), so the file it writes is owned by an account `agent` cannot write as. A login shell that prints anything of its own (a prompt, a banner) writes onto the channel the copy's rsync or scp handshake reads, which breaks the transfer before a byte moves. The guest does ship `rsync` (NixOS's default packages), but `limactl cp` never used it, so it was no fallback either.

`yo cp SRC... DST` replaces both with scp, run as the agent over the same `ssh_options` every other `yo` ssh goes through. The ownership problem never arises, and the transfer runs no guest shell, so the prompt problem cannot corrupt a file. (A download also runs `find` in the guest to leave build output out, through the agent's login shell. A prompt or banner there makes the listing malformed, and `yo cp` stops with an error that names the record. See "A guest listing is untrusted".)

### No shell runs, and why that holds

`yo` arranges the "no shell" property by passing `-s` to scp, which makes it speak the sftp protocol whatever its default is. OpenSSH 9.0 and later default to sftp, but earlier releases default to the legacy protocol, which runs `scp` in the agent's login shell on the guest; the flag keeps the property independent of the Mac's OpenSSH version (it needs 8.7 or later). sshd then answers a `yo cp` connection by spawning `sftp-server` directly. No login shell, the agent's or the operator's, runs for the transfer itself; the one `find` a download runs is the exception, below.

`nix/base.nix` leaves NixOS's default `allowSFTP = true` untouched, and that default is the whole reason this works. Turning sftp off would break `yo cp` with no other symptom to point at. The command also uses no `yolobox-guest` subcommand, so unlike the subcommands that do, it needs no box rebuild first and works against a box of any version.

### Operands

The guest side of an operand always starts with `:`, and `yo` never guesses which side is which. `yo cp --help` has the spellings. A copy has no existing-ancestor fallback the way a missing mirrored directory does, so `resolve_cp_operands()` requires every source on one side and the destination on the other. It refuses anything else outright: no colon anywhere, sources on both sides, or a copy entirely inside the guest. Each message names the remedy, plain `cp` or `yo enter`.

Two refusals are worth recognising on sight:

- A relative guest spelling (`:` or `:x`) issued from a Mac cwd outside `$HOME` has no mirror to extend. It is refused with `:~/...` named as the fix.
- A guest path that resolves outside `/home/agent` (or, for an absolute spelling, outside `/tmp`) is refused the same way `guest_path` refuses it everywhere else in `yo`.

### The `/tmp` exception

`/tmp` is accepted for absolute spellings only (`CP_GUEST_ROOTS`). Claude Code's scratchpad is `/tmp/claude-<uid>/...`, so an agent's scratch output, screenshots and exports are what a person most wants to pull to the Mac, and none of it is under the home. The relative, `:~` and bare `:` spellings keep the home-only check, so `:../../../tmp` is still refused.

Moving `TMPDIR` under `~` instead was rejected for two reasons. It changes the environment of every program in the box. And the two places age differently: `/tmp` has systemd's `q /tmp 1777 root root 10d`, which removes files untouched for ten days, while the home has no aging at all and would keep every scratch file until something deleted it. Letting scp reach `/tmp` widens nothing real, because scp runs as `agent` and that account's own permissions are the boundary, not `yo`'s path check.

### The multi-source case

scp itself requires the destination to be a directory once more than one source is given. That is why `cp_mkdir_target()` runs `mkdir -p` against the destination itself, rather than its parent, whenever there is more than one source, DST is `:`, or DST ends in `/`. The rule is scp's, not one `yo` invented.

### What reaches scp's argv

The aim is that neither a file name on the Mac nor one in the guest can steer scp.

- A Mac operand is made absolute by `local_cp_operand()`, which joins it onto the cwd and does not normalise it. That settles two cases at once: `a:b.png` is a path, not host `a`, and a name that starts with `-` is not an option. The operands also sit after a `--`. Normalising is wrong because collapsing a `..` lexically would change which file a symlinked spelling means.
- A guest source is glob-escaped by `scp_glob_escape()`, because scp expands wildcards in a remote source itself.
- A guest destination is deliberately not escaped. scp never globs a destination, so the backslashes would be taken literally and create a file named `a\[1\].txt`.
- An empty operand is refused outright, since joined onto the cwd it would mean the directory itself.

### Uploads refuse symlinks

`scp -r` follows symlinks and uploads what they point at. A link an agent left in a repo (`leak -> ~/.ssh/id_ed25519`) would therefore copy a file the user never named into the guest. `refuse_symlinks_in()` walks each source without following links before anything leaves, and the first symlink stops the copy, before even the `mkdir -p` in the guest. A source that cannot be read is refused by name too, not skipped.

The guest side is not checked. The test exists to keep the Mac's private files from entering the guest, and a guest source is something the agent could already read, with that account's own permissions as the boundary. A trailing slash on an upload source is stripped before the check, because `lstat("link/")` follows the link and would hide a symlink.

### Downloads stage, then merge

A download never lets scp write onto the Mac destination itself. scp writes through a symlink it finds there, and the agent controls what a repo it pushed contains. With `notes -> ../../.zshrc` committed, pulling the repo on the Mac and then running `yo cp :proj ~/src/` would overwrite `~/.zshrc` through the link.

`download_from_guest` instead has scp fill a `.yo-cp-*` staging directory beside the destination, inside it when it is an existing directory, so the final move is a rename on one filesystem. `plan_merge` then plans every entry against what is already on the Mac before anything moves, and `land_staged` renames the entries into place. The refusals you will see:

- `refusing to copy over symlink "<path>": the copy would overwrite its target "<target>", not the link`, for an existing symlink at any depth.
- A file meeting a directory, or the reverse, is refused the same way.
- `cannot place <staged> -> <target>: <reason> (N of M entries already landed)`, when `os.replace` fails, for example on a mount point or a read-only Mac directory. It is never a traceback.
- `destination "<path>/" is not a directory`, when DST ends in `/` and does not exist. scp itself says "No such file or directory" there, and an earlier `yo` created a file named `newdir`.

The staging directory is removed on every path, a refusal, an scp failure and a failed move included. `-p` keeps a guest directory's mode, and sftp-mode scp creates each local directory with that mode `| S_IRWXU`. `unlock_tree` adds `u+rwx` anyway to each real directory before `shutil.rmtree`, so whatever mode scp left (a read-only Go module cache) can be walked and removed. It never follows a symlink, which would chmod a Mac file. If cleanup still fails, `download_from_guest` prints that failure on stderr and re-raises the original error. It never replaces it.

### Downloads never land control paths

A pulled guest tree is code the agent wrote, and some of its file names make the Mac execute it. A `.git/config` with `core.fsmonitor`, `core.pager` or `core.hooksPath` runs as the operator on the next `git` command in that directory, with no prompt, and `.git/hooks/*` does the same. `.envrc` runs under direnv, and `.vscode` and `.idea` carry editor tasks that auto-run. Without the filter, `yo cp :proj .` would lay the guest's `.git` over the Mac's, because `plan_merge` lets a file replace a file: a guest-to-host code execution path through the one command meant to be safe for pulling work back.

`drop_control_paths` runs once on the staging directory, after scp and before `plan_merge`. It removes every entry whose name is `.git`, `.hg`, `.svn`, `.envrc`, `.vscode` or `.idea` (`LANDING_CONTROL_NAMES`), at any depth, and prints `yo: skipped "<path>": ...` on stderr for each. The match uses Unicode case folding (`casefold()`), because APFS folds names that way, so `.vſcode` is skipped like `.vscode`. It prunes the staging tree instead of filtering the move list because a directory that does not exist on the Mac yet moves as one rename and never passes through `plan_merge`'s per-entry walk, so a `new/.git/config` would have slipped in. Everything else lands as before, ordinary overwrites included. The list is deliberately short. A name is on it only when the host runs what it holds with no prompt on the next `git` command, `cd` or editor open. Project files that other tools run only after a trust prompt (`.claude`, `.mcp.json`, `.devcontainer`, `.zed`) are not on it; a repo's content belongs on the Mac through `git pull`, not `yo cp`. If you do want a repo's history on the Mac, `git pull` is the path.

### Downloads never land build output

A pulled tree also does not carry the directories the project's own tooling recreates: `node_modules`, `.venv`, a Rust `target` and a Next.js `.next`. They dwarf the source, and the host does not want the guest's compiled artifacts or interpreter links anyway. They are left out on the guest, so their bytes never cross the wire: scp has no exclude option and takes a directory whole, so `fetch_guest_sources` asks first and fetches second. Each skipped directory prints `yo: skipped "<path>": build output is never copied to the host; the project's tooling recreates it` on stderr.

`node_modules` and `.venv` are skipped by name. `target` is skipped only when a regular file `Cargo.toml` sits beside it, and `.next` only when `package.json` does. This is the reasoning behind the guest's `gc`: the name alone proves nothing, and a `target` with no `Cargo.toml` may be a directory of data. Only a real directory counts, so a file or a symlink called `node_modules` lands, and a manifest that is itself a directory does not satisfy the rule.

The sources you name on the command line are exempt. `yo cp :~/proj/node_modules .` lands `node_modules`, because you asked for exactly that. Only what is found inside a named source is judged. Existing host content is untouched, because the skipped directory is never staged: a `node_modules` already on the host keeps every file and gains none.

How it works, in three steps, all as the agent over ssh (ssh runs `find` through the agent's login shell, as it already runs the `mkdir -p` of an upload. The arguments are quoted, so no name in the tree can steer the command, but the shell and the agent's `PATH` are the agent's, so what `find` prints is untrusted, see "A guest listing is untrusted" below. The transfer itself is still scp over sftp with no shell):

1. `find_build_output` runs `find -H SOURCES -mindepth 1` with a `-printf` record per match and reads back the candidate directories and the manifests beside them. `node_modules` and `.venv` are pruned, so find never walks them. `target` and `.next` are walked, because a `target` that proves nothing may hold a `node_modules` of its own. The verdict (is the manifest there?) is made on the Mac, and only the outermost directory of a nested pair is reported. A record is `kind TAB mode TAB mtime TAB path NUL`, because a path may hold a newline, a tab or any byte but NUL.
2. No build output found: one scp of the sources, exactly as before. Otherwise the directories on the way down to build output are the only ones scp cannot take whole. A second `find -maxdepth 1` lists them and their children.
3. `fetch_walked` makes each of those directories itself, with the mode scp -p would have given it (the guest mode plus `S_IRWXU`, as sftp-mode scp makes it) and the guest mtime, then asks scp for the children one by one: a child that holds no build output is a whole tree, and scp takes it with `-r -p` as ever. The children of one directory go in batches of at most `SCP_ARGV_BUDGET` bytes, measured as scp receives them (`host:` and glob escapes included), so a directory of thousands of entries cannot overflow the command line. A fifo or socket among them is passed over with a note naming it relative to the source, like every other skip, because scp passes one over inside a directory but fails when it is named on its own.

Everything else is unchanged: each guest path is still glob-escaped for scp (find gets it unescaped; it never globs), everything still lands in staging beside the destination, and `unlock_tree`, `drop_control_paths` and `plan_merge` run on the result as before. The control-path skip stays on the Mac and not in the find, because only the Mac knows how APFS folds a name. A symlink in the tree is followed by scp, as it was before, and what a link to a directory points at is not searched for build output.

### A guest listing is untrusted

`find` runs through the agent's login shell, and the agent owns its shell rc files and its `PATH`. So a `find` can print anything: the agent can make a guest `find` lie. A forged record such as `/home/agent/proj/a/../../../z/node_modules` is a build-output path that, joined to a source, climbs out of it. Used to build an scp source, it fetches a file the operator never named (`/home/agent/proj/a/../../../.envrc`) straight into the staging tree, past `drop_control_paths` and `plan_merge`, which only judge what the walk of a named source brings.

`list_guest` therefore treats the whole output as input to validate, and `parse_guest_record` raises a `YoError` that names the record (`repr`, so an escape sequence in it cannot drive the terminal) for each of these:

- a record that does not match `type TAB octal-mode TAB decimal-time TAB path` exactly (a banner, a truncated line, `nan`, `0o7`, `1_0`);
- a path that is not clean (`posixpath.normpath(path) == path` fails: a `.` or `..` component, an empty one, a trailing slash) or is not strictly under a named source (the second listing also prints the sources themselves, and only they may appear as-is);
- two different accounts of one path (overlapping sources print a path twice, alike, and that is fine);
- in the build-output listing, a record find was not asked for: a directory not named like build output, a file not named like a manifest, or any other type.

Anything the first listing says is also checked against the second. `fetch_walked` raises when a walked directory is missing from the second listing, is no longer a directory, or has no entries, because the first listing found build output in it. That is how a real race looks too (npm deleting `node_modules` between the two finds), so the message says the tree changed and to copy again.

A listing can still lie by omission or by pointing at a clean path that is not what it says, and that is harmless: a path under a named source is something the operator asked for, and everything fetched still passes `drop_control_paths` and `plan_merge`.

The list is `BUILD_OUTPUT` in `yolobox_cli/cp.py`, a map from directory name to the manifest it needs, or `None`. `tests/test_consistency.py` keeps it equal to the arrays in `nix/guest/yolobox-guest.sh` (`BUILD_DIRS`, `REMOVED_OUTRIGHT`, `NEEDS_MANIFEST`) that `gc` uses.

## The host driver

Everything that differs between host OSes sits behind one object, `state.driver()`: where a machine's files live, the 1Password socket, the ssh port that reaches the initrd, the keepalive pid the AWS broker watches, the VM's status, config gaps, host gaps, start, stop, disk size and growth, and the words of each printed remedy that names a host tool. The `Driver` protocol in `yolobox_cli/driver.py` lists the members. `LimaDriver` is the macOS one and `LibvirtDriver` the Linux one.

`main()` is the only place that chooses. It passes `HOST_PLATFORM` (`sys.platform`, read once at import) to `driver_for()`, hands the result and the machine name to `set_box()`, which builds the frozen `Box(driver, name)`. The per-machine names (`box.editor_ssh_block`, `box.include_line`, `box.include_re`) and the state directory `state.instance_dir()` derive from the driver's `instances_dir`. A command that needs no box (`yo help`) skips both. Nothing else looks at the host OS, so no helper can disagree with the choice. `box` has no default: a path that forgets to choose raises `AttributeError` (`state` has no `box` yet) instead of quietly driving Lima.

`driver_for()` returns `LIMA` for `darwin` and `LIBVIRT` for `linux`, and refuses any other `sys.platform`.

The Lima code is `yolobox_cli/lima.py`: `lima_instance_exists` (the one place that decides whether the instance exists: its exact name is a line of `limactl list -q`, and a failing listing is a `YoError`, never "no instance") and `lima_instance_info` (`None` only when the name is not listed; any failure of `limactl list NAME --json`, or an answer that is not one JSON object, is a `YoError` naming limactl's output, so a broken limactl is never read as a box with no gaps; `current_size` raises the same way on a failing `limactl list`; `show_status` instead returns a warning line with the exit code, which `yo status` reports and carries on) and its helpers plus the `LimaDriver` methods (`config_gaps`, `fatal_gaps`, `config_gap_message`, `start`, `stop`). Callers outside it reach it only through `state.driver()`, and tests patch the methods on `yo.LIMA`. The tests load the package through `load_yo()`, which sets `config.HOST_PLATFORM` to `darwin` and installs the Lima driver, so they run the same on a Linux CI host. `tests/test_yo_libvirt.py` loads its own copy with `driver_for("linux")` and a `FakeHost` that plays virsh.

### The libvirt driver

One libvirt domain per machine on `qemu:///system`, named `yolobox-NAME` and tagged with a `yolobox:instance` metadata element (namespace `https://github.com/aka-rider/yolobox`) holding NAME. `yo` finds its domains by that tag, never by name. `libvirt/domain.xml` is a `string.Template` filled by `domain_xml()` with the name, the ssh port, the account's uid and gid, the memory in GiB and the vCPU count; the host side it relies on is explained in [linux/host-setup.md](linux/host-setup.md). The domain has no graphics, vsock, filesystem, channel, hostdev or tpm, and `config_gaps()` reads the live `virsh dumpxml` and reports anything that is not on an allowlist of the template's root elements and device tags (so also `shmem`, `redirdev`, a root-level `qemu:commandline` and the rest, see [Config gaps are fatal](docs/linux-host.md#config-gaps-are-fatal)), a seclabel that is missing, does not relabel, or (for the static DAC one) does not carry `+UID:+GID` of the current `yolobox-vm` account, a missing tag, a `portForward` that is not bound to 127.0.0.1, or a network that is not exactly one `type='user'` interface with a passt backend. On this driver every gap is fatal: `fatal_gaps()` returns all of them, so `vm_up` raises with `config_gap_message()` before it asks for the passphrase or starts anything (Lima's returns only the `ssh.overVsock` gap, `LIMA_FATAL_GAPS`, and only prints a note for the rest). `yolobox_domains()` looks only at the tag of a domain it does not know, so another tool's domain is never read strictly. A domain undefined between `virsh list --all` and its `dumpxml` is skipped, as `dominfo` does for the memory count (`require_undefined`); a `dumpxml` that fails for a domain still listed is an error.

- **Files.** The instance directory is `~/.local/state/yolobox/instances/NAME`: `operator.pub`, the staged cidata, `domain.xml`, `ssh.config`, `known_hosts`, and the two ssh control sockets. Nothing else is written, and never a private key. A `disk.done` file left by an earlier `yo` is ignored, and is safe to delete.
- **The operator key.** A 1Password SSH Key item titled `yolobox-operator` must be the one agent identity with that comment (none or two is an error). `yo` writes its public half to `operator.pub` and into the cidata's `user-data`. `ssh.config` names `operator.pub` as the `IdentityFile` and 1Password's socket as the `IdentityAgent` with `IdentitiesOnly yes`, so ssh signs through the agent. `initrd_ssh_argv()` does the same for the pre-unlock probes through `state.driver().initrd_identity_agent()`, where Lima says `none` and uses its private key file.
- **The cidata.** `cidata_files()` builds `user-data`, `meta-data`, `lima.env` (no blank line; `LIMA_CIDATA_UID` is 501) and an empty `etc_environment`. The user-data `ssh-authorized-keys:` block has the shape the initrd's awk program in `nix/luks/yolobox-initrd-authorized-keys.sh` reads, and a test runs that program on it. `xorriso -as mkisofs -V cidata -J -R` makes the ISO, uploaded as the raw pool volume `yolobox-NAME-cidata.iso`. It is rebuilt only when the staged text changes or the volume is gone, and only while the VM is stopped. A host account name the guest cannot use as the operator (empty, not a plain lowercase name, or `agent`) is refused before anything is created.
- **The disk.** The first start downloads the pinned seed image to `~/.cache/yolobox/`, checks its sha512 (also on every later use), uploads it as the pool volume `yolobox-NAME.qcow2` and resizes it to the box's disk size. Completion is judged by capacity, which only the last step sets: the volume is created at the seed's size (4.7 GiB), and only the resize after a successful upload takes it to the box's size, never below `MIN_DISK_GIB` (40 GiB). An upload that fails for any reason, Ctrl-C included, deletes the half-filled volume. `disk_volume_finished()` decides whether an existing volume is kept: it is when its capacity is at least `MIN_DISK_GIB`. A finished volume is adopted as it is; any other volume is one an earlier run did not finish (an interrupt, a failed resize), and is deleted and rebuilt with a note on stderr. The cidata is built in a temporary directory and replaces the staged copy only after the upload succeeded, so a changed operator key is rebuilt on the next run when an upload failed.
- **The size.** `yo up` and `yo bootstrap` take `--memory GiB`, `--disk GiB` and `--cpus N`, carried as `Size` (`yolobox_cli/driver.py`, `None` for a flag not given). `vm_up` is the one place both drivers decide what they mean; see [Sizing a box](#sizing-a-box-both-drivers). On libvirt a missing domain is created at the asked size: `domain_size()` fills the defaults in, 16 GiB of memory (`LIBVIRT_MEMORY_GIB`), a 100 GiB disk (`LIBVIRT_DISK_GIB`) and `default_cpus()` CPUs, and `create_domain()` puts memory and CPUs into the template. An existing stopped domain is changed in its definition: `resize()` runs `virsh setmaxmem`, `setmem` and `setvcpus --maximum` then `setvcpus`, each with `--config`, so the next start reads them. The maximum goes first and the current value follows, because libvirt refuses a current value above the maximum. That keeps the domain, its UUID, its port and its nvram, which a redefinition from the template would not promise. A bigger disk is `grow_disk()`, run by `grow_running_disk()` (see [Sizing a box, both drivers](#sizing-a-box-both-drivers)): `virsh vol-resize --pool default VOLUME NG` on a shut-off domain only (it refuses any other state, because qemu holds a running domain's image open), and `current_size()` reads the memory and CPUs from `virsh dominfo` (`Max memory`, `CPU(s)`) and the disk from the volume's `Capacity`. A memory that is not a whole number of GiB is an error, never rounded into a false match. `resize_refusal()` applies the same fit-on-this-host rule as creation to a changed memory (`memory_refusal`: the asked memory plus the `Max memory` (`virsh dominfo`) of every other active domain on `qemu:///system`, `virsh list --name`, so paused ones count and shut-off ones do not, must be at most the host's `MemTotal` in `/proc/meminfo` (`libvirt_host.host_memory_bytes()`) less `HOST_MEMORY_RESERVE_GIB` (4 GiB) for the host itself). A box that keeps its memory is not judged again, so a CPU-only change is never refused for the host's memory. The refusal names MemTotal, the reserve, each other domain with its memory and the most this box can have. Those virsh calls only read, and they run before the passphrase. A `dominfo` without a `Max memory: N KiB` line is an error, never a domain that takes nothing; a `dominfo` that fails is an error too, unless the domain is no longer defined, when it is not counted. A domain removed with `virsh undefine` leaves its finished volume behind, which the next start adopts at its own size; `creation_refusal` therefore refuses an explicit `--disk` that differs from that volume's capacity. For a bigger one it says to drop `--disk` and then run `yo disk-grow N`, which keeps what is on the disk; for a smaller one it says a disk cannot shrink, and names the `vol-delete` that builds a new one at the loss of the data. `--memory` alone passes there, because the new domain gets it. Every virsh runs through `libvirt_host.virsh()` or `spawn_virsh()` with `LC_ALL=C`, because virsh translates what it prints and `yo` parses it. `redefine_command()` is the one spelling of "remove the definition, keep the volume" (`yo down && virsh undefine --nvram`), used by the gap message and the lost-domain hint. See [Sizing a box](docs/linux-host.md#sizing-a-box).
- **The ssh port.** `host_port_window()` is every port above the second field of `/proc/sys/net/ipv4/ip_local_port_range`. The kernel never uses it as a source port and no registered service lives there. The box's forward takes the lowest port in it that nothing holds on 127.0.0.1 (a bind probe) and no yolobox-tagged domain forwards. `state.driver().ssh_port()` reads it back from the domain. A window that is empty makes `yo` refuse to run. Choosing and taking a port is one step under `port_lock()`, an `flock` on `~/.local/state/yolobox/instances/.port.lock`: `create_domain()` holds it from the choice to `virsh define`, and `forward_port()` from the choice to the end of `ssh -O forward`, so two `yo` processes never pick the same port.
- **Start and unlock.** `virsh start` leaves no process behind, so `unlock_disk` runs without a starter and treats any state but running as failure. Its waits poll the unlock itself, never a sleep tied to libvirt. `wait_for_operator` reads `domstate` between its probes too, so a domain that dies after the unlock ends the wait at once, with the error described in [A domain that dies under yo](docs/linux-host.md#a-domain-that-dies-under-yo). The driver's `vm_lost_hint(status)` writes the second half of that error: it gets the status `vm_status()` read, `None` when the domain no longer exists. Before every send of the passphrase, `run_initrd_helper` calls `state.driver().verify_initrd_listener(port)`. On libvirt that runs `ss -ltnHe 'sport = :PORT'` (the `uid:` field needs no root) and raises unless every listener on the port belongs to `yolobox-vm`, the account that runs the domain's passt; with no listener yet it passes, since ssh then finds nothing to talk to. Nothing pins the initrd's host key, so this owner check is what stops another local account from squatting the port and receiving the answer. Lima's check is a no-op: its hostagent runs as the host user.
- **Stop.** `stop()` starts one `virsh event NAME lifecycle --loop --timeout 300` before it asks for `virsh shutdown`, and never re-arms it. It reads `virsh domstate` right after arming and after every line the watcher prints, and returns when the state is exactly `shut off`; the events only wake the loop, the state is the judge, because libvirt also reports a shutdown notice before the stop. `in shutdown` (and `running`, `blocked`) keep it waiting; `paused`, `pmsuspended` or a state `yo` does not know ends it with an error that names the way out, since such a guest never finishes shutting down by itself. The watcher ending first is either virsh's own `event loop timed out` (exit 1: "did not shut down within 300 s", with the `virsh destroy` recovery) or a virsh failure, reported with its stderr. A stop that lands in the milliseconds before virsh registers the watcher is still missed when it falls after the first `domstate` read; see [Stopping the domain](docs/linux-host.md#stopping-the-domain).
- **The broker's keepalive.** `keepalive_pid()` is the pid of the operator's ssh master (`ssh -O check`), which `vm_services` re-creates on every healing command (see [Which commands heal](#which-commands-heal)). See [docs/aws.md](docs/aws.md#broker-lifetime).
- **Preconditions.** `require_tool()` runs before every command and checks, in this order, virsh, the system connection, a libvirt daemon of 12.2.0 or newer (the `Running against daemon:` line of `virsh version --daemon`, not the client's version), `yolobox-host.service` active, the account `yolobox-vm` and the port window. Each failure is its own message and names the installed `linux/host-setup.sh`. The operator key and the passt socket directory's ACL (`passt_dir_gap()`, which needs `getfacl`) are checked when the VM starts, not on every command, so `yo status` works while 1Password is locked or after another passt domain reset the ACL mask.
- **Growing the disk.** `yo disk-grow N` works here: the same `cmd_disk_grow`, with `grow_disk()` above for the ceiling.

## yo port

`yo port GUEST_PORT` is the Linux way to reach a guest port from the host. It takes the lowest free port of `host_port_window()` the same way the ssh forward does, under the same lock, runs `ssh -O forward -L 127.0.0.1:HOST:127.0.0.1:GUEST_PORT` over the operator's master, and prints `127.0.0.1:HOST`. The forward lives as long as that master. A guest port outside 1-65535 is refused by the parser. On macOS the command exits 64: lima already mirrors guest ports 1024-49151 by itself, except the fixed OAuth callback ports of common CLIs (1455-1457, 8020, 8085, 9005 and 18000), which `lima/yolobox.yaml` ignores so that a guest listener cannot squat the port a host login tool expects to bind (see [lima/yolobox.md](lima/yolobox.md#which-guest-ports-reach-the-host)).

### The nix environment

Every nix command on the box needs the operator's name and the flake ref: `flake.nix` throws without either. It also takes the machine's hostname, which defaults to `yolobox` when unset, and `yo` always sets it, because a named machine rebuilt without it would be renamed back to `yolobox`. The third word is the flake ref the rebuild builds from (`YOLOBOX_FLAKE_REF`, a full `github:OWNER/REPO/REF` as `flake_ref()` returns it). It is required, not optional, because the box stamps it into `/etc/yolobox/flake-ref` and a rebuild without it would delete the stamp, so a later rebuild from inside the box would have nothing to read. `nix_env(username, ref)` builds the three words from `NIX_ENV_USERNAME`, `NIX_ENV_HOSTNAME` and `NIX_ENV_FLAKE_REF`, and `cmd_bootstrap` and `rebuild_hint()` both use it, so the two spellings cannot drift. The host OS is not among them: the guest is never told which host runs it ([nix/base.md](nix/base.md#no-host-os-in-the-guest)). Inside the box, `yolobox-guest rebuild switch|boot` sets the same three variables from the box's own stamps, and `TestGuestRebuildMatchesYoAndTheBox` keeps its names and its ref pattern equal to `yo`'s. The command itself is built once, by `nixos_rebuild_argv()`, and its flags are `NIX_REBUILD_FLAGS`, `--impure --refresh`, which the printed hint and the guest helper spell the same way. `--refresh` matters where nix is given the ref by name, because a branch moves and nix would otherwise reuse an hour-old fetch of it: in `locked_rev()`, the `nix flake metadata --json --refresh` that `yo bootstrap` runs in the box before it builds, which prints `building <ref> at <commit>`; in the printed `rebuild_hint()`; and in `yolobox-guest rebuild`. The bootstrap's own build does not depend on it, because `nixos_rebuild_argv(action, username, ref, rev)` names the commit that `locked_rev()` resolved (`github:OWNER/REPO/<rev>#yolobox`), while `YOLOBOX_FLAKE_REF` stays the branch ref so the box stamps the branch it follows. The commit is not stamped into the system, so a docs-only commit keeps the generation (see [docs/distribution.md](docs/distribution.md#a-branch-that-moved-built-at-its-old-commit)).

## Starting and unlocking

Starting the VM is more than one `limactl start`. The root disk is encrypted, and lima's own start blocks until its ssh works, which needs the disk unlocked. So `vm_up` derives the passphrase first (`luks_passphrase`, which asks 1Password for the `yolobox-disk` key and so shows a Touch ID prompt), starts `limactl start` in the background, and hands the passphrase to the initrd with `unlock_disk` once the initrd's sshd answers. It then waits for the stage-2 sshd to accept the operator. Both waits read `vm_status()` between probes: a VM that is not Running any more (a lima instance whose hostagent died) ends them at once with `<name> is <status>, not Running, while yo waited for ...`, followed by the driver's `vm_lost_hint()`, which on Lima names `limactl list`, `~/.lima/<name>/ha.stderr.log` and the console log `serialv.log`, or, for an instance that is no longer listed, how to create it again (`yo up` for the default one, the `limactl create` line for any other). While waiting for the operator, an ssh failure of no known shape, or a login whose `true` exits non-zero, is raised at once, not retried, but only after the VM's status was read: a VM paused or killed during a connected probe fails it with a keepalive timeout, and the lost-VM error says more than ssh does. A VM that is running and already accepts the operator needs no passphrase and no prompt. `LimaDriver.limactl_stop()` is the one place that runs `limactl stop` (for `stop()` and `force_stop()`), with a timeout and the caller's own recovery text for its known hang; everything else stops the VM through `state.driver().stop()` (see "The host driver"). Every pre-unlock probe goes through `initrd_ssh_argv()` and `sshd_answers`, never a pinned ssh role. `boot_stage()` combines them (stage 2 first, then the initrd), and `yo status` runs it before `account_status()`, so a locked box prints `disk: locked` with no host-key warning. The reasons, the protocol and the failure shapes are in [docs/disk-encryption.md](docs/disk-encryption.md).

`yo down` (`vm.cmd_down`) asks `boot_stage()` first. An `UNKNOWN` answer (an sshd without the stage-2 banner mark refused both the operator and `root`; on libvirt a dead 1Password causes it, on Lima an initrd without its keys or a stage 2 from before the mark) stops nothing: `cmd_down` prints `unknown_stage_message()`, which names the login problem when there is one (`login_problem()`; only libvirt has an agent to name), and the driver's login fix (`login_fix()`: 1Password on libvirt, lima's key file on Lima), then says to run the command again so that `initrd_state()` decides; it never offers a forced stop, because a refusal proves nothing about whether the initrd is encrypting ([docs/linux-host.md](docs/linux-host.md#the-operators-key)). A box that answers in its initrd has no ACPI handler, so a polite shutdown there would run into the 300 s stop timeout on both drivers, and a forced one is a power cut. The first boot's in-place encryption runs in that same initrd, behind the same sshd, so `boot_stage()` alone cannot tell an idle wait from it. `cmd_down` therefore asks `unlock.initrd_state()`, which runs one probe command in the initrd (`INITRD_PROBE_COMMAND`) and judges its output (`classify_initrd_probe`, pure): the state of `yolobox-luks-migrate.service` (a oneshot unit, `activating` for the whole run of the migration script), the pending `ask-password` entries, and whether a `yolobox-unlock` FIFO exists in `/tmp`. The table:

| migrate unit | pending asks | unlock helper | state | `yo down` |
|---|---|---|---|---|
| `activating` | not the migration's own | any | `MIGRATING` | refuses, no command offered |
| any | any | running | `UNLOCKING` | refuses, prints the force-stop command |
| `failed` | any | none | `MIGRATION_FAILED` | refuses, prints the force-stop command |
| `activating` | the migration's ask (nothing written yet) | none | `WAITING_FOR_PASSPHRASE` | `force_stop()` |
| `active` | only the disk's `cryptsetup:` ask | none | `WAITING_FOR_PASSPHRASE` | `force_stop()` |
| `active` | none | none | `UNLOCKED_IDLE` | refuses, prints the force-stop command |
| anything else, a failed probe, unexpected output | | | `UNKNOWN` | refuses, prints the cause and the force-stop command |

The probe's output is self-delimiting: a `migrate=` line, one `unlock-fifo=` line per `/tmp/yolobox-unlock.*`, each ask file between `ask-begin` and `ask-end` (a newline is printed before the end marker, so a file without a trailing one cannot glue onto its neighbour), and a closing `probe=end`. `classify_initrd_probe` refuses anything outside that grammar. `initrd_state()` returns an `InitrdReading` (the state and, for `UNKNOWN`, the cause: the ssh exit code and stderr, or the output no state matched), which `yo down` and `yo status` both print. `tests/test_yo_luks.py` runs the real command under `sh` against a stand-in initrd.

Only `WAITING_FOR_PASSPHRASE` is powered off by yo itself: `limactl stop --force` on Lima, `virsh destroy` on libvirt (a domain already off is left alone). Every other initrd state raises a `YoError` that says why; it never falls back to the polite stop, which would hang, and never kills by itself. The refusal is state-specific so that it is never a dead end: for every state but `MIGRATING` it prints the driver's own force-stop command (`Driver.force_stop_command()`, one method) and says when running it is safe. `MIGRATING` gets none, since nothing makes the kill safe there. The states that can last forever are the reason: `UNLOCKING` is a leftover FIFO of a `yo up` that died, `MIGRATION_FAILED` and `UNLOCKED_IDLE` are the initrd's emergency mode after a failed migration or after `HELPER_EXIT_ROOT_MOUNT_FAILED` ("stop and start the instance"). `yo status` runs the same probe and says which state the locked box is in. The probe reads systemd's own state, so it needs no new guest script and works on a box built before it existed. Every other stage, and no answer at all, takes the polite `stop()`, which on both drivers returns at once for a VM that is already stopped (Lima reads `vm_status()` first; an instance limactl does not know still goes to `limactl stop`, whose refusal surfaces).

**The unlock lock.** Between the probe and the kill, a second `yo up` could answer the migration's ask, and the kill would land mid-encryption. `state.unlock_lock(wait)` closes that: an exclusive `flock` on `~/.local/state/yolobox/NAME.unlock.lock`, one file per machine. `run_initrd_helper`, the one function that sends the passphrase to the initrd (so `yo up`, `yo bootstrap` and `yo disk-grow` all pass through it), holds it for the whole helper run, waiting if it is taken. `cmd_down` takes it without waiting, holds it across the probe and `force_stop()`, and when it is taken refuses with "another yo is unlocking this box" instead of blocking. `cmd_destroy --yes` does the same for its whole run, so a `yo up` that is sending the passphrase is never destroyed under. No command deletes the lock file, `destroy` included, for the reason `state.unlock_lock` gives. A `yo up` that waits in `unlock_disk` between two helper runs holds nothing, so `yo down` may then power the box off; that is the operator's own decision and `yo up` fails with the driver's error. The lock is per host: two hosts driving one box are not supported.

## Which commands heal

Before the command body, `main()` calls `forwards.vm_services()` once for the commands whose subparser sets `heals=True`: `ssh`, `enter`, `cp`, `code` and `zed`. It re-creates the operator's ssh master, makes sure the AWS broker runs and re-issues the 1Password and broker reverse forwards (see [docs/ssh.md](docs/ssh.md#healing-reverse-forwards)). The other commands are exact about it: `up`, `bootstrap` and `disk-grow` heal through `vm_up` (bootstrap calls `vm_up(run_services=False, size=...)` and then `vm_services()` itself, once, after the reboot decision); `aws-check` calls `ensure_aws_broker` itself; `down`, `destroy`, `status`, `gc`, `port` and `help` never heal. `status` in particular must report a broken forward, not repair it before it looks.

A box that cannot be reached stops the command with the "is it up?" hint (`sshx.Unreachable`). Any other healing failure (the broker, a forward, missing units) is printed as a warning and the command runs anyway, because `yo ssh` is the way into a box whose forwards are broken, and a heal that blocked it would lock the operator out of the repair. A box that predates the proxy units prints the note that names `yo bootstrap` and proceeds.

## Several machines

`yo -m <name> <command>` (or `yo <command> -m <name>`) makes `yo` drive the lima instance `<name>` instead of `yolobox`. Any number of machines can exist and run side by side, each addressed by its own `-m`. Without the flag nothing changes. The flag is accepted before or after the command, and when it is given twice the last one wins.

It is a flag, not an exported variable, on purpose. An exported variable stayed set in the shell and carried a second machine's name into every later command, including ones meant for the default box. A flag sits on the line that acts on it. For `yo ssh`, a `-m` before the first guest word is `yo`'s; from the first non-option word on, everything reaches ssh untouched.

Every per-machine name derives from that one value through `Box`, the one place that derives them, so no name is left over from another machine:

- the lima directory `~/.lima/<name>` (ssh config, `known_hosts`, the multiplexing sockets), and every `limactl` call;
- the ssh host `lima-<name>`, and the herdr machine and ssh alias `<name>`;
- the instance's own `ssh.config`, which the one `Include ~/.local/state/yolobox/instances/*/ssh.config ~/.lima/*/ssh.config` line in `~/.ssh/config` reaches for every machine;
- the guest's hostname and tailnet node name: `yolobox` for the default machine, `yolobox-<name>` for any other (`hostname_for()`, passed to nix as `YOLOBOX_HOSTNAME`). Lowercased, because DNS labels are case-insensitive and tailscale lowercases them, so `-m Work` and `-m work` would collide on the tailnet (the libvirt domain stays `yolobox-Work`, `Box.vm_name`).

A name follows lima's rule (letters and digits joined by single `.`, `_` or `-`), narrowed to what also makes the hostname `yolobox-<name>` a DNS label: only single `-` joins, at most 55 characters. It must not start with `lima-`. Otherwise instance `lima-x` would name its herdr alias `lima-x`, which is the ssh host of instance `x`. `yo` refuses any other spelling while it parses the command line, with exit 2 and the usage text, before anything runs. An instance made earlier with a `.` or `_` in its name is refused too, because no DNS label holds them; `limactl` still manages it.

**An existing named machine is renamed at its next bootstrap.** Until now every box was `yolobox`, whatever its instance name. The next `yo bootstrap -m NAME` sets the hostname to `yolobox-NAME`, so its tailnet node is renamed to match (the old `yolobox.<tailnet>.ts.net` name for that node stops resolving). The value is chosen by the operator's own `-m NAME`, validated twice (by `yo` while parsing `-m`, then by `flake.nix`), and shows up only as the guest hostname, the tailnet node name and the hostname in the guest's DHCP request on the NAT.

**The instance must exist.** `yo` creates only the default instance, from `lima/yolobox.yaml`. For any other it stops in `vm_up`, before it asks 1Password for the disk key and before it starts anything, and prints the command to run:

```sh
limactl create --name <name> --set '.ssh.localPort=<port>' lima/yolobox.yaml
```

Add `--cpus`, `--memory` and `--disk` to size it. `yo up --memory 24 --disk 250 --cpus 3` (or `yo bootstrap` with the same flags) on a missing default instance creates it at that size: `LimaDriver.start()` runs `limactl start --name yolobox --tty=false --memory 24 --disk 250 --cpus 3 lima/yolobox.yaml`. `lima/yolobox.yaml` sets the memory (16 GiB) and the disk (100 GiB) but no CPU count, because a number that fits every Mac cannot be written there: `vm_up` always asks for `default_cpus()` when `--cpus` is not given. On a missing instance of another name `yo` still stops before the passphrase and prints the `limactl create` command with the flags you gave (and `--set` for the port), because only its creator can choose its port; run it, then run the same `yo` command again without the flags. The command always carries `--cpus` (the flag you gave, else `default_cpus()`, since Lima's own default is not yo's), and the line about dropping flags names only the flags you gave. See [Sizing a box](#sizing-a-box-both-drivers) for what the flags do to a box that exists. Give it at least 8 GiB of memory: the system is evaluated and built inside the instance, and a smaller one gets the nix evaluator OOM-killed (the build dies with `Killed`, exit 137). Give it at least 40 GiB of disk: the box takes a 16 GiB swapfile by default (`yolobox.swapSizeMiB` in `nix/swap.nix`, whatever the disk size) plus the nix store of its first build, and a smaller disk fills up to 100 percent. The failure does not say "disk full". `dhcpcd` gets "No space left on device" when it rewrites `/etc/resolv.conf` (through resolvconf), which is left empty, so nothing resolves and a `tailscale up` retries forever with "failed to resolve". If a small instance is unavoidable, a `/etc/yolobox/local.nix` line `yolobox.swapSizeMiB = 2048;` shrinks the swapfile (`0` for none; no `mkForce`); free the space first (`swapoff` and remove `/var/swapfile`), and run `sudo systemctl restart dhcpcd` once to refill `resolv.conf` (see [docs/disk.md](docs/disk.md#a-full-disk-looks-like-a-dns-failure)). Give every instance its own free `<port>`. `yo` has to know the port that reaches an instance's initrd sshd before the first start, and `state.driver().ssh_port()` is the one place that answers: 60022 for the default instance, and for any other the `ssh.localPort` that `limactl list <name> --json` reports. A port of 0, which makes lima pick a new one on every start, or a missing or malformed one, is an error, and so is one below 49152, which lima's mirror of guest ports could hand to another box's listener (see [lima/yolobox.md](lima/yolobox.md#one-port-per-instance)). Choose `<port>` in 49152-65535. `yo` never guesses: the default box answers on 60022 and accepts the same lima key, so a fallback would probe, and unlock, the wrong machine.

**What bootstrap adds per instance**, all of it removed by `yo destroy` except the first item and the lock file:

- the `Include ~/.local/state/yolobox/instances/*/ssh.config ~/.lima/*/ssh.config` line at the top of `~/.ssh/config`, once for every machine on the host, and only when `ssh_config_reaches_box()` finds the box unreachable. `yo` asks first when it has a terminal, and otherwise prints the line;
- a herdr machine with the target `<name>` (`herdr machine list --json` shows it). `yo destroy` removes it with `herdr machine remove` and the `id` of the entry, which `forwards.herdr_machine_id` finds: the one parser of that listing, shared with `ensure_herdr_machine`. A matching entry without a string `id` raises in both, naming `herdr machine list --json` to inspect it and `herdr machine remove` to delete it by hand; the parser never guesses which machine to remove, and `yo bootstrap` stops on such an entry until it is gone;
- the remembered flake ref `<name>.flake-ref` and the unlock lock file `<name>.unlock.lock`, under `~/.local/state/yolobox/`. `yo destroy` removes the first and never the second (see below);
- the machine's instance directory, which holds `ssh.config` and the rest of the per-machine ssh files. On Lima it is `~/.lima/<name>/`, which `limactl delete` removes: the editor block `Match host lima-<name> user agent`, the host-key pin block and the herdr alias `Host <name>` (all re-applied to `ssh.config` on every `yo` run), and `known_hosts` with the guest's host keys. On libvirt it is `~/.local/state/yolobox/instances/<name>/`, which `yo destroy` removes itself, with `ssh.config`, the operator key, the staged cidata and both ssh masters' control sockets.

Each instance's blocks live in that instance's own `ssh.config`, so writing one never rewrites another, and a second bootstrap of the same instance changes nothing.

**`yo destroy`** deletes a machine, and everything on it is lost. `destruction_steps()` builds the one list of `Removal(what, remove)` pieces that exist now, and it is printed without `--yes` and walked with it, so the listing cannot differ from what is removed. The list is the agent account's ssh master (`sshx.agent_master_removals()`; both drivers open one at `ssh-agent.sock` inside the instance directory, and it must quit before that directory goes), then `Driver.removals()`, then the herdr machine and the flake-ref file. On Lima `Driver.removals()` is the one `limactl delete --force`, which stops a running instance and removes `~/.lima/<name>`. On libvirt it is the operator's ssh master (closed under `master.lock`, so no `ensure_master` reopens it in between), the power-off, `virsh undefine --nvram`, the two volumes and the instance directory. A piece that does not exist is not listed, and a machine with none left prints that it has nothing to destroy and exits 0, so the command can be run again after a failure part-way. A step that fails raises and stops the run; nothing is swallowed. A running box is powered off at once, without the initrd and encryption check of `yo down`, because everything on its disk is being deleted. With `--yes` the whole run, list included, holds the unlock lock without waiting: a `yo up` can start a box that is off, so a list made before the lock could leave a running domain at its undefine. The lock does not stop a `yo up` from running `virsh start` before it sends the passphrase, so on libvirt the undefine step (`LibvirtDriver.undefine_domain`) reads the domain's state when it runs and powers the domain off first if it is active, whatever the list said; undefining a running domain would leave qemu on the volume the next step deletes. It refuses while a `yo up`, `yo bootstrap` or `yo disk-grow` is sending the passphrase. The lock file stays. A `yo up` blocked in `flock` holds the file's old inode, so a deleted file would let the next yo lock a fresh one beside it and lose the exclusion; like `instances/.port.lock`, it is a few bytes of host state. libvirt's `master.lock` does go with the instance directory; a yo that races destroy for it finds no `ssh.config` afterwards and fails with ssh's error. `destroy` leaves what the machines on a host share: the `Include` line in `~/.ssh/config`, the downloaded base image under `~/.cache/yolobox`, `instances/.port.lock` and the AWS broker's socket and logs. Because destroy deletes `<name>.flake-ref`, every hint that tells the operator to delete the box (`state.destroy_then_bootstrap_command()`, used by `require_agent_account()`) prints the `yo bootstrap` that follows with `--version <ref>` when a ref is remembered. `TODO.md` lists the host-global state that several running boxes still share: the LUKS key, the AWS broker and the mirrored host ports.

### Sizing a box, both drivers

`--memory`, `--disk` and `--cpus` (`add_size_arguments`) on `yo up` and `yo bootstrap` become a `Size`, and `vm_up` decides what it means, before the passphrase, with `Driver.vm_status()`:

- **No such box.** It is created at the asked size. Once `creation_refusal()` has judged the flags as given, `Size.for_creation()` fills in the default CPU count, `default_cpus()`: `min(4, N - 1)` for a host of N CPUs, always leaving the host one. A host with one CPU, or one whose count `os.cpu_count()` cannot read, creates nothing (an error before the passphrase). Both drivers get the same decided `Size`.
- **A box that exists.** `plan_resize()` reads `Driver.current_size()` (a `BoxSize`: memory and disk in GiB, CPUs) and compares each asked field with it. A flag equal to the current value, or not given, changes nothing, and a start with no flag does not even read the size, so the box keeps what it has. If nothing differs, `yo up` goes on as it always did.
  - A smaller `--disk` is refused, naming the current disk and saying that neither lima nor libvirt can shrink one.
  - Any change while the box is not stopped (`status != driver.off_status`: Running, in its initrd, paused, starting, broken) is refused, naming what the box has now, which flags would change it and `yo down`. Nothing is ignored silently.
  - A stopped box is changed after the passphrase is derived, so a missing 1Password key leaves it as it was, and before it starts: `Driver.resize(memory_gib, cpus)` sets memory and CPUs. `Driver.resize_refusal()` is the host's say on the new memory, read-only, so it also runs before the passphrase. The box then starts as usual.
  - A bigger disk is not touched by `vm_up`. `yo up` (`cmd_up`) and `yo bootstrap` call `grow_to_asked_disk()` once the box is up: if the disk is smaller than asked, `grow_running_disk()` does what `yo disk-grow N` does, which is to check `require_growable_guest()` while the ceiling is untouched, derive the passphrase, stop the box, raise the ceiling (`Driver.grow_disk()`), start it, and grow the mapping and the filesystem (`grow_mapping_and_filesystem()`: `cryptsetup resize` with the passphrase, `resize2fs`, then the checks). `yo disk-grow N` on a running box calls the same `grow_running_disk()`. So `yo up --disk N` costs a second boot, and that is the price of knowing before the ceiling moves: no host-side fact says whether the guest can grow (a remembered flake ref exists only after `bootstrap --version`, and the generation and the encryption live inside the box), so the box boots first and a guest that cannot grow (no `growpart` unit, root not encrypted yet) is refused with the ceiling as it was. `grow_running_disk()` is the only place that says what to do after a failure. If the host refuses the ceiling edit after the box was stopped, it says the box is stopped with its old disk and names `yo up --disk N` to try again. Once the ceiling is raised, asking for the same disk again changes nothing, so any later failure (the restart, `cryptsetup resize`, `resize2fs`) ends with "the disk limit is already N GiB; finish growing it with: yo disk-grow N", and keeps the original exit code. A guest that cannot grow is refused before the ceiling moves, with the same `yo disk-grow N` as the next step once it can: memory and CPUs may already have been applied and the box is running, so a rerun of `yo up --disk N` would be refused as a change to a running box. That refusal, for a running box whose only change is a bigger disk, offers `yo disk-grow N` beside `yo down`.
  - A rerun of `yo up --disk N` on a box already at N does not trust the ceiling alone: `grow_to_asked_disk()` asks `root_has_room_to_grow()`, which reads, without the passphrase, whether the partition fills the ceiling and whether the LUKS mapping and the filesystem fill the partition and the mapping (within `MAPPING_SLACK_BYTES`). If one is short, an earlier grow stopped after the ceiling moved, and the rerun finishes it with `finish_previous_grow()`, the same code as `yo disk-grow N` at the ceiling the box has. A root that is not encrypted yet (a box just created) has no mapping and nothing to finish; a partition short of the ceiling is the `growpart did not grow it` error, never a silent exit 0.
  - `yo bootstrap --disk N` on a box that exists does that grow after its build and reboot, not after its first start. The first encrypted generation does not grow into a raised ceiling by itself: the shipped image grows the partition only at its first boot, `growpart` is a stage-2 unit of the built generation that grows the partition and nothing else, and the mapping and filesystem of an encrypted root grow only with the passphrase, which `yo` holds. A box that bootstrap just created is already at its size, so nothing is grown.
- **`yo disk-grow N`** reads the ceiling from `current_size()` too. A smaller N is refused. N equal to the ceiling finishes a grow that failed after the ceiling edit (it boots the box, checks, and grows the mapping and filesystem). A bigger N is `grow_running_disk()`; the box is stopped by it before `grow_disk()`, which only ever works on a stopped one.

`lima` applies memory and CPUs with `limactl edit --tty=false NAME --memory N --cpus C` and the disk with `limactl edit --tty=false NAME --disk N`; libvirt as described in [the libvirt driver](#the-libvirt-driver). Lima's `current_size()` reads `limactl list NAME --format '{{.Memory}} {{.Disk}} {{.CPUs}}'`: memory and disk in bytes, CPUs a count. Memory and disk must be whole GiB (`driver.exact_gib()`), or it is an error, since a rounded value could make a different size look equal. libvirt's `current_size()` is `dominfo` plus the volume's `Capacity`, read the same way.

## bootstrap --version

`yo bootstrap --version REF` chooses what the box builds from. Without it the box builds from this `yo`'s own release, `github:aka-rider/yolobox/v<version>`, so a `brew upgrade` moves the next bootstrap with it. The value is resolved while the command line is parsed (`flake_ref()`), so a refused one (`yo bootstrap --version 1.7`) exits 2 with the usage line before `limactl` is looked for. Exactly three spellings are accepted:

- `1.7.2` or `v1.7.2` is that release tag.
- `main`, `my-branch` or `v1.7.2-rc1` is a branch or tag on `aka-rider/yolobox`. It has no `/`, starts with a letter or digit and contains only letters, digits, `.`, `_` and `-`.
- `github:OWNER/REPO/REF`, with exactly those three parts: owner and repo of letters, digits, `.`, `_` and `-`, and a ref as above.

Everything else is refused before anything runs, with one usage error. That includes `path:`, `file:` and `git+file:` refs, an absolute path, a `#` (which would smuggle a second flake attribute into `nixos-rebuild --flake <ref>#yolobox`), and `github:owner/repo` without a ref. A partial version such as `1.7` or `v2` is refused because a release is `X.Y.Z`. `latest` is refused because no such ref exists upstream, and this `yo`'s own release already is the latest one after an upgrade. An empty value or one with spaces is refused, and so are `~` and `./` spellings. On an unreleased build (`YO_VERSION` is `dev`) `--version` is required, because there is no release to fall back on.

**A release older than 1.9.2 is refused too** (`FIRST_HOST_OS_FREE_RELEASE`, `old_release()`), as `1.9.1`, `v1.9.1` or `github:aka-rider/yolobox/v1.9.1`, the owner and repo matched case-insensitively as GitHub does. Those flakes throw unless `YOLOBOX_HOST_OS` is `darwin` or `linux`, and this `yo` no longer passes it ([nix/base.md](nix/base.md#no-host-os-in-the-guest)), so the build would fail in nix after the reboot decision. The usage error names the release and the command that bootstraps with that release's own `yo`, `nix run github:aka-rider/yolobox/v1.9.1 -- bootstrap`. `yo`'s own release goes through the same check (`own_release_ref()`): an unreleased build of `main` still carries the last release in `.version`, and it is treated like `dev`, so `--version` is required. `rebuild_hint()` does the same for a remembered ref of such a release: instead of a rebuild that would fail, it offers `yo bootstrap` to move the box to this `yo`'s release (`yo bootstrap --version <ref>` when this `yo` has none) or the old release's own `yo` to keep it there. The hint is worded to follow the "rebuild it:" and "switch it:" its callers put before it. A branch, a tag that is not `vX.Y.Z`, or a fork's ref carries no version `yo` can compare, so it is not checked. One cut before the host OS left the flake needs a `yo` of the same age.

There is no spelling for a checkout in the guest, on purpose. A checkout in the guest is owned by the agent, so the agent could commit a `wheel` grant before the build, and `nixos-rebuild` runs as root; that is why the VM never builds from a checkout (CONSTITUTION). To build a fork or a branch, push it to GitHub and name it with `github:OWNER/REPO/REF` (see [docs/distribution.md](docs/distribution.md#flake-ref-not-a-checkout)).

**The ref is remembered per machine.** A flag does not persist, so `yo bootstrap --version REF` writes the ref it built to `~/.local/state/yolobox/<name>.flake-ref` after `nixos-rebuild` succeeds. `rebuild_hint()` reads that file first, so a remedy printed for a box built from a fork keeps naming the fork's ref. Without the file it falls back to this `yo`'s release. A blank file counts as no file. A ref in it that `flake_ref()` no longer accepts (a `path:` ref written by an older `yo`) is not used: `rebuild_hint()` leaves it out of the hint, prints one line that names the file and says the stored ref is no longer accepted, and falls back to this `yo`'s release. It does not raise, because the hint is built while another error is being reported. The file holds only an explicit `--version`. A bootstrap without it means this `yo`'s release, so it deletes the file: otherwise the ref of an old fork build would pin the box against every later `brew upgrade`, and the next hint names this `yo`'s release again.

## The guest helper

`yo bootstrap` reads the profile and booted generations without the helper, over plain ssh (`guest_generations`), because the nixos-lima image a first bootstrap starts from has no `yolobox-guest` yet. Reading them through the helper would make that first bootstrap die with a version-skew error before its reboot into LUKS.

`guest_helper(role, sub, args)` runs a `yolobox-guest` subcommand over ssh as the operator or the agent, and turns a missing helper or subcommand into a version-skew note instead of a bare exit code. Nothing in it asks for root. The reasons are in [nix/guest/yolobox-guest.md](nix/guest/yolobox-guest.md#version-skew).

`sshx.guest_out(argv)` is the plain-ssh read of a command's output (the generations above, the root device's type, `growpart`'s unit state, the partition sizes). It goes through `sshx.probe`, so ssh's exit 255 is `Unreachable` with the "is it up?" hint and never an empty string: an empty answer means the command ran on the box and printed nothing. `yo status` turns that `Unreachable` into a warning line, `disk: cannot reach ...`. The two `df` reads of `disk-grow` keep ssh's own words (`guest_root_usage` quotes the exit code and stderr) and `disk-grow` adds the hint to the first.

### Whether the agent account exists

`sshx.account_status()` never infers a missing agent account from a failed `ssh agent true`: the agent's own `~/.bashrc` can exit non-zero and fail that probe on a box that has the account. When the agent probe fails and the operator's works, it asks the box, `getent passwd agent` as the operator, and only exit 2 (key not found) is `operator_only`, the box that predates the operator/agent split and gets the `yo destroy --yes && yo bootstrap` advice. Exit 0 is `agent_failing`: `require_agent_account()` prints the probe's exit code and stderr, points at the account's shell startup files and does not name `yo destroy`, which would lose unpushed work for a fixable rc file; `yo status` prints it as an `agent:` warning. Any other `getent` exit is a `YoError` naming it.

## The network line and the gateway-blocked marker

`yo status` prints one `network:` line, built by `network_status_line()` from the two results of `yolobox-guest net-check`: whether egress works and whether lima's gateway answers a DNS query. The pair tells a VPN on the host that owns its default route from one that blackholes the gateway (see [docs/host-network.md](docs/host-network.md#vpn-shapes)).

### The egress line

The `egress:` line above it comes from one `systemctl show -p LoadState -p ActiveState yolobox-egress`, because `systemctl is-active` prints `inactive` for a unit the box has never heard of and would make an old box look like it was in a fallback tier (see [nix/egress.md](nix/egress.md)). The line is built by `egress_status_line()`:

- `LoadState=not-found` prints `egress: box predates the egress table; run yo bootstrap`, a warning.
- `LoadState=masked` prints `egress: WARNING the egress table is masked` with the `systemctl unmask` command, because a masked unit loads no table at the next boot.
- A probe that answered nothing (ssh failed) or an unrecognised `LoadState` prints `egress: not checked — the probe answered …` with the exit code and ssh's stderr. That is not a warning: a failed probe says nothing about the box and must not read as a fault.
- A loaded unit that is `active` reads the live table (`EGRESS_TABLE_PROBE`, `sudo -n nft list table inet yolobox-egress` over the operator channel), because a table that was flushed, replaced or emptied by hand leaves the unit `active` and `egress: host and LAN blocked` would then be a lie. `egress_table_holds()` checks structure only: an `output` hook chain, an `oifname { "lo", "tailscale0" ... } accept` rule, and `reject` rules for the private IPv4 and IPv6 ranges. It never compares rule content, because `lanAllow` and `tunnelInterfaces` boxes legitimately add accepts and a `postrouting` chain (`tests/fixtures/egress-tunnel.nft` is the test's proof). A table that fails the check, or nft's "No such file or directory", prints `egress: WARNING unit active but table looks wrong`. Any other probe failure (ssh down, sudo asking for a password) says nothing about the table, so the line stays `egress: host and LAN blocked`.
- A loaded unit in any other state is not vouched for by the unit, so `yo` reads the live table here too. It judges the structure first (`egress_table_holds()`): the unit has no `ExecStop`, so a unit stopped by hand leaves the full table loaded, and its chain is a plain `chain output {` like an old recovery table's. A table that holds prints `egress: WARNING full rules loaded, unit yolobox-egress <state>` with the restart command. Otherwise the table says which fallback the box is on (`egress_tier()`). The tier is the chain's whole header line: `chain output_recovery {` is the **recovery table** (no network), `chain output_lastresort {` the **last-resort table** (loopback, established and related flows and DHCP only), and no table at all (nft's "No such file or directory") is **no table (fail-open)**, the state in which the box may reach the host and the LAN. A plain `chain output {` under an inactive unit is a recovery table too: boxes built before the tiers existed called their recovery table `output`. The headers are compared as whole lines and never as prefixes, because all of them begin with `chain output`. A probe that failed some other way says the live table could not be read, and a table that is none of the three says so. Every one of these is a warning that ends with the rollback command, the unit's journal and the `nft list table` command.

A third line, `rootdisk=full`, is the only thing `network_status_line()` checks before the pair: a full root disk leaves dhcpcd unable to write `resolv.conf`, which reads as a dead network, so the line names the disk and the `yo gc --yes` remedy instead of blaming a VPN. A box that prints no `rootdisk=` is read as not full, because nothing is known about it ([nix/guest/yolobox-guest.md](nix/guest/yolobox-guest.md#net-check-and-the-gateway-blocked-marker)).

The gateway result has a third value, `Gateway.SKIPPED`. A box that blocks lima's gateway by design creates `/etc/yolobox/gateway-blocked`; while that file exists `net-check` prints `gateway=skipped`, and `yo` says so in the line: `network: ok (lima's gateway probe skipped: this box blocks it by design)` when egress works, and `network: WARNING guest egress is dead (lima's gateway probe skipped: this box blocks it by design)` when it does not. Without the marker a refused probe would read as a VPN fault that is not there. The marker is the whole contract: `yo` never learns why the gateway is blocked, and the repo creates the file nowhere.

### The `yo status` exit code

`yo status` exits 1 when it printed any warning, so a script or a CI check can tell a healthy box from a sick one without reading the text. Each warning goes through `Report.warn`, which prints the line and records it; the pure line builders (`egress_status_line`, `network_status_line`, `tailscale_status_line`, the disk lines) return a `StatusLine` carrying the text and whether it is a warning, so a new line cannot be a warning in the text and not in the exit code. These warn: an unreachable box (`vm: unreachable`, also the lost-while-probing case), a root disk that is not encrypted, a guest disk 90 percent full or more, version drift between this `yo` and the box (printed on stdout with the other lines), a missing proxy unit or a dead 1Password or AWS guest forward, a stale or unreachable AWS broker, config gaps, host gaps (`Driver.host_gaps()`, each one a `<driver>: WARNING ...` line; on Linux the passt socket directory's ACL), every egress line above that is not `host and LAN blocked` or `not checked`, and the `WARNING` network and tailscale lines. These do not: tailscale not installed or waiting for a login, `aws: disabled`, and a probe that could not run (`not checked`). A box locked in its initrd is `vm: unreachable` plus `disk: locked`, so it exits 1.

### Version drift has a direction

`release.version_drift()` compares the box's `/etc/yolobox/version` with this `yo` as X.Y.Z numbers (`1.10.0` is newer than `1.9.0`, which text order gets wrong). A box built by an older release, or by one that cannot be ordered (`dev`, `1.3`, anything but plain digits), is advised `yo bootstrap`. A box built by a newer release than this `yo` is advised to upgrade `yo`, because `yo bootstrap` builds this `yo`'s own release and would downgrade it. A `dev` host never reports drift. `yo status` and the version-skew note of a missing guest subcommand (`helper_skew`) both use it.

## One parser

`build_parser()` is the single declaration of `yo`'s command line: `add_subparsers` plus `set_defaults(func=cmd_x)` per subcommand. `main()` parses, picks the host driver and runs its tool preflight, then calls `args.func(args)`. Every command function takes the parsed `argparse.Namespace`.

`yo help [command]` is `yo [command] --help`: the same text, printed through `out()`. `yo help` with no topic prints the top-level help. It skips the driver and its preflight, as `--help` does, so it works on a host without lima. It is a real subcommand, not a flag alias, so that `yo help <command>` is one word per command with no leading dashes, and so `yo help bogus` fails with argparse's usual `invalid choice` usage error.

One declaration means no second list can drift from it (a hand-written usage string beside a command table) and no command body carries its own copy of the arity check. Every command with no positional arguments rejects extra ones the same way, so `yo up bogus` fails like `yo down bogus`.

`disk-grow`, `--memory` and `--disk` validate their size through `whole_gib()`, an argparse `type=` callable that accepts only `proc.is_ascii_number` digits for a value above 0, the same chokepoint the guest port goes through. `int()` alone would also take ` 40 `, `+40`, `4_0` and non-ASCII digits such as `٤٠`. Every refusal, `-1` and `0` included, reads "must be a whole number of GiB greater than 0". `--cpus` goes through `box_cpus()`, which takes the same digits only and holds the value to 1 through one less than the host's CPU count (`driver.host_cpu_count()`, `os.cpu_count()`), so the host keeps a CPU. Anything else, the count itself included, is a usage error that names the range and the host's count; a host with one CPU has no range and says so, and a count `os.cpu_count()` cannot read is an error, never an open range.

### `yo ssh` keeps `REMAINDER`

`yo ssh`'s trailing arguments are declared `nargs=argparse.REMAINDER`, and the choice is load-bearing. `rebuild_hint()` prints `yo ssh sudo YOLOBOX_USERNAME=$(id -un) … nixos-rebuild switch --impure --flake '…'` as the documented remedy for a stale generation. If argparse ever parsed `--impure` as its own flag instead of passing it through, the tool's own printed advice would stop working.

Verified against real argparse: every invocation whose first token is not option-like passes through untouched, `yo ssh sudo … --impure --flake …` included. A leading-dash first token is handled by argparse before REMAINDER starts. `yo ssh --help` and `yo ssh -h` print `yo`'s own ssh help and exit 0. Any other leading option, such as `yo ssh -v`, exits 2 without reaching the VM. Nothing here changes what ssh receives, because REMAINDER only hands the tokens after the first non-option word to ssh as the remote command.

### `yo ssh` allocates a pty only on a terminal

`cmd_ssh` passes `-t` when stdin and stdout are both terminals and not otherwise. An interactive `yo ssh htop` keeps its pty; `yo ssh cmd > file` does not, because a pty on redirected output turns every newline into CRLF and the file is corrupted. `cmd_enter` refuses outright when either end is not a terminal ("stdin or stdout is not a terminal"), since it exists to give an interactive shell and ssh would otherwise print "Pseudo-terminal will not be allocated" and run the login shell without a pty; both commands read the one rule from `session.on_terminal()`.

### `allow_abbrev` stays off

`allow_abbrev=False` is set on the top-level parser and on every subparser, so `yo gc --de` and `yo gc --y` are rejected as unknown arguments. argparse accepts prefixes by default. For a command whose job is deleting things, a flag that two keystrokes of a typo can reach is one too many. A new subparser added without it makes `--de` work again on that command, with no error anywhere.

### Empty string is not no argument

`enter`, `code` and `zed` take `project` as `nargs="?"`, so `yo enter ""` and `yo enter` produce different values, `project=''` against `project=None`, and they are different invocations. The first is an empty fzf query, the second mirrors the guest twin of the current directory. `target_dir` therefore branches on `project is not None`, never on truthiness, so the empty string does not collapse into the no-argument case.

## Output filter

`out()` and `err()` are the two functions every line `yo` prints goes through. They replace C0 and C1 control characters with `?`, except tab and newline (`CONTROL_BYTES_RE` in `yolobox_cli/common.py`, applied by `common.sanitize`). Guest output is attacker-controlled: ssh stderr, a path the helper reports, a project name, whatever a failing guest command says. It reaches the operator's terminal on the Mac, which acts on escape sequences. A title change, a cursor move that overwrites a line of the message above it, and an OSC 52 that sets the clipboard are all possible.

`out()` and `err()` can only turn a control character into `?`, and they leave a newline alone, so a file name that holds `\n` could still start a forged `yo: ...` line, and a `?` does not say what the name held. That is what `ui.shown(name)` is for. Every message that quotes a name the guest chose (a skipped build directory or control path, a `fifo` passed over, a move or merge refusal naming a pulled entry, the landing directory the guest reported) wraps the name in it. A plain name comes back unchanged. A name with a control character, a bidi override or an undecodable byte comes back with Python's backslash escapes (`a\x1b[2J\nb`), as one printable line. `as_pulled()` does it for the three cp skip messages. A new message that quotes a guest name goes through `ui.shown`, as one that prints guest text goes through `out()` and `err()`.

Filtering at one chokepoint, instead of at each call site that happens to print guest text, is what keeps a new message from forgetting. It is a display filter only. What `yo` runs and writes to files is never altered by it, and a command that must hand bytes through untouched (`yo ssh`, `yo enter`) does not print them via `out()` at all.

Output streamed live goes through it too. `yo gc` and `yo aws-check` show the guest tiers as they run, and the tiers print project paths and whatever a project's `make -n clean` or `make clean` recipe prints. So `run_filtered()` pumps their stdout and stderr line by line into `out()` and `err()` instead of handing ssh the terminal.

`pick_project()` runs each guest-listed project name through `common.sanitize` before handing the list to `fzf --read0`, so the picker's safety does not depend on the installed fzf stripping control bytes. A name that contained one comes back from the picker with `?` in its place and so names no real directory.

## YO_VERSION

`YO_VERSION = "dev"` in `yolobox_cli/config.py` must survive as that exact literal assignment, unreformatted. `nix/pkgs/yolobox.nix` overwrites it with `--replace-fail` and `homebrew/yolobox.rb` with `inreplace`. Both match the literal text, and either patch is how a release build gets its real version baked in.

Reformat that line by reflowing it, requoting it or changing its text in any way, and the Nix build fails loudly at `--replace-fail`, which is the safer failure. The brew formula's `inreplace` can silently no-op and ship a binary that still reports `dev`. `TestYoVersionLiteral` fails when `config.py` stops having exactly one line that is that literal, and a consistency test fails when either packager patches a different file than the one holding it, so the reformat is caught before the release, not by it.
